# 통합 보강 및 실제 검증 — 2026-09-30

**범용 자율 데이터 분석 agent의 전체 출시 판정은 NO-GO다.** 이번 통합 작업으로 원격 최신행 수치 히스토그램, 그룹 결과 정렬, 대용량 계획 시 불필요한 전체 데이터 읽기, 평가 도구의 잘못된 감점을 수정했다. 실제 화면과 Databricks를 연결해 검증했다. 남은 구현·평가 묶음은 [작업 보드](workboard.md)의 1~4번이다. 이 개수는 작업량이나 완료율을 뜻하지 않는다.

## 변경된 동작

- 원격 최신행 분포를 범주 빈도뿐 아니라 2~100개 동일 폭 수치 구간으로 처리한다. 스키마를 먼저 확인하고 키별 최신행 선택·동률·결측·전체 입력 수·구간 빈도를 한 SQL에서 계산한다. 전체 원본 대신 작은 집계 결과를 받는다.
- 1~4개 명시적 복합 키, 로컬/원격 구간 설정, “구간 수만 6개로 바꿔줘” 후속 요청을 연결한다. 동일 분석은 검증된 receipt와 저장 결과를 재사용한다.
- 실제 막대의 위치·폭·높이와 독립 NumPy 히스토그램을 대조한다. 빈 구간도 유지하며 최댓값은 마지막 구간에 포함한다. 잘못된 경계·합계·계보·이미지는 완료로 인정하지 않는다.
- 영속 데이터의 자료형은 Parquet 메타데이터로 확인한다. 숫자 컬럼 판별 때문에 큰 원본을 pandas로 읽지 않는다. 실행 단계의 모든 연산이 부분 scan으로 바뀐 것은 아니다.
- 그룹별 평균/중앙값/건수의 독립 oracle 5개를 추가했다. 이 검증에서 발견한 “평균 내림차순” 누락을 수정했다. 정렬 지표를 모호하게 추정하지 않고, 계산 결과의 정렬 계약도 완료 시 검증한다.
- 실제 재시작에서 발견한 모델 선택 초기화를 수정했다. 명시적으로 선택한 모델을 대화별 SQLite 설정으로 저장하며 새 대화는 로컬 기본값을 유지한다. 다른 열린 탭이 다시 렌더링되기만 해서는 저장된 선택을 덮어쓰지 않는다. AppTest로 선택·세션 재생성·대화 전환·이전 탭 재실행을 검증했다.
- 데이터별 이름은 외부 fixture/관측 스키마에서 가져온다. 특정 테이블 이름을 공통 agent 코드에 넣지 않았다.

## 실제 Databricks 및 웹

`remote_histogram.json`은 실제 `workspace.default.bank_loan` 750,000행에서 `job`별 최대 `id` 행의 `age` 분포를 계산했다. 최대 ID를 실제 시간이라고 가정하지 않고 요청한 정렬 기준으로 사용했다.

- 12개 키, 8개 구간, 내려받은 결과 9행(검증 헤더 1행 포함), 22.793초.
- 독립 `ROW_NUMBER` SQL + NumPy 정답과 실제 빈도·경계 일치. 빈도 `[2, 2, 1, 4, 2, 0, 0, 1]`.
- 스키마/집계/독립 정답 SQL 총 3회. 같은 요청 반복은 추가 SQL 0회.
- 이 명확한 요청은 결정적 도구 경로로 처리해 모델 호출 0회다. 임의 자연어에 대한 모델 성공률로 해석하지 않는다.

별도로 **실제 Streamlit 입력창**에서 스키마 조회 → 8구간 → “구간 수만 6개로 바꿔줘” → 같은 후속 요청 반복을 실행했다. 결과를 미리 심지 않았다. 6구간에서도 같은 12개 키를 유지했고 빈도는 `[3, 2, 4, 2, 0, 1]`이다. 장부는 스키마 1회+집계 2회, 총 3회 완료이며 반복 시 늘어나지 않았다. 원격 원본 전체 로딩은 없었다. 실제 이미지는 [화면](browser_followup.png), 저장 계약/SQL digest는 [웹 여정](browser_journey.json)에 있다.

새 CLI·웹 검증의 warehouse SQL은 합계 **6회**다. 전날 범주형 검증 8회와 중복 합산하지 않는다. 공개 Spider SQLite 실행과 모델 serving 호출도 이 횟수에 넣지 않는다.

## 대용량 보존 검증

[100만행 검증](streaming_million.json)은 합성 cursor를 실제 제품 적재·graph에 연결했다. 네트워크/모델 호출은 없다.

- 100만행 파일 적재 2.908초, 최대 batch 1,024행, 전체 peak RSS 452,509,696바이트(약 431.5 MiB).
- 원본 평균 → 조건부 평균 → 원본 평균+히스토그램이 독립 정답과 일치했다. 모든 단계 원본 보존.
- 50,176행 후 전송 중단, byte 한도 실패에서 부분 결과 미발행·이전 선택/원본 보존·staging 정리 확인.
- 저장소 재개 후 원본 100만행과 선택 보존.

5컬럼 합성 데이터와 현재 호스트에서의 결과다. 임의 너비의 원격 대규모 데이터나 모든 EDA 연산의 메모리 상한을 보증하지 않는다. 이전 실제 10만행 로딩·로컬 최신행 100만행 근거도 보존되어 있다.

`reference_200.json`은 실제 설정 모델을 연결한 graph 실행이지만 로컬 완전 fixture를 사용한다. `group_final.json`은 마지막 정렬 경계 보강 후 5개 재실행이다. agent 구현을 정답으로 삼지 않고 원래 reference 계산 및 독립 비교를 사용했다. 미채점 coverage를 통과율로 바꾸지 않았다.

Spider 평가 adapter는 SQL **제안**만 받아 공식 scorer가 공개 SQLite에서 실행하는 구조다. 제품의 자동 DB 실행 기본값이 adapter로 유입되던 오류를 수정했다. 제품의 자동 읽기 정책은 유지한다. 수정 후에도 역할별 조인/JSON/복잡한 범위를 제대로 계획·검증하지 못했고 제출된 2개 SQL도 오답이었다. 올바른 SQL까지 차단하는 계약 제한과 모델이 잘못 계획하는 문제가 모두 있다. 이를 단순 LLM 문제로 돌리거나 검증을 해제해 통과시키지 않았다.

## 채점기 실패도 보존

- 로컬 `qwen3:8b` judge는 확장 통제 문항 12개 중 5개가 시간 초과였다. 실제 답변 3개도 채점 오류였다. 오류를 0점 또는 통과로 바꾸지 않았다.
- 초기 Databricks judge는 정답의 표기·언어를 사용자 요구로 오해해 4개 양성 통제를 감점했다. 첫 보정은 수치 오답 하나를 잘못 통과시켰다.
- 공통 채점 기준을 “사용자 요구의 출처는 INPUT, 수치 정답의 출처는 EXPECTED_OUTPUT”으로 분리했다. 최종 기본 12개 및 별도 새 문항 8개에서 양성/음성 모두 올바르게 판정했다. [최종 보정](judge_calibration_authoritative.json), [새 문항](judge_heldout.json), [실제 답변](deepeval_calibrated.json).
- 첫 평가·실패·보정 파일은 덮어쓰지 않고 별도 보존했다. 이 20개 통제의 성공이 모든 judge 신뢰성을 입증하는 것은 아니다.

## 출시 판정

검증된 범위에서 로컬 단일 사용자 테스트는 가능하다. **범용 GO는 아니다.** 최신행 선택 전후 필터·동률/결측 처리의 후속 연결, 역할별/다단계 SQL, 대용량 D07/D08·J21~J24 전체 계약, 독립 oracle 98개가 남아 있다. 별도 서버 배포는 사용자 지시로 제외한다. 원래 요청의 필수 조건을 줄여 GO라고 선언하지 않는다.
