# 범위 조건·출처 결합 보강과 실제 재검증 — 2026-10-03

`education이 primary 이고 age가 30~40인 사람들을 시각화 해줘`를 기존 실패 대화에서 다시 실행해 실제 나이 분포 이미지를 확인했다. 추가로 실제 화면에 들어온 `primary과 secondary` 요청 및 같은 조건의 후속 차트도 완료했다. 이번 결과는 이 요청군의 수정 근거이며 범용 분석 agent의 전체 GO 판정은 아니다.

## 원인

- 기존 범위 추출기는 뒤에 `범위/구간`이 없는 `30~40인`을 놓쳤고, 미해석 범위로 표시하지도 않았다. 모델의 올바른 `BETWEEN 30 AND 40` SQL을 부분 해석된 조건과 비교해 거절했다. 오류 `84d23ebed6f2`는 이후 Ollama 응답 대기의 ReadTimeout이며, 당시 DB 제출은 없었다.
- 원본 데이터가 선택되지 않은 대화에서 여러 테이블의 `Age/age`를 합쳐 양쪽 조건을 요구했다. 단순 표현 패턴 수정만으로 해결되지 않았다.
- 추가 요청의 복수 범주 조건도 누락됐고, 같은 출처의 독립 빈도 결과 두 개를 원본 분기 충돌로 처리했다. 중간 run `d8b1b304711848e785ce29346626ee00`는 모델이 조건을 포함한 SQL을 제안했으나 검증기가 거절하고 203.230초 뒤 timeout으로 끝났다. 이 실패는 성공으로 계산하지 않았다.

## 구현

1. 공통 범위 문법과 원문 누락 감지를 추가했다. 물결/대시/to/between/부터/에서/이상·이하, 음수·소수·천 단위 구분을 처리한다. 날짜·문자열·축 설명·내부 UUID는 범위로 오인하지 않는다.
2. 명시된 테이블 또는 선택한 데이터의 스키마에 조건을 결합한다. 선택이 없으면 원문 컬럼들의 정확한 이름이 한 출처에 함께 존재해야 한다. 출처가 둘 이상이면 임의로 정하지 않는다. 제품 코드에 재현 테이블/컬럼 이름을 하드코딩하지 않았다.
3. SQL 검증 불일치 시 원래 사용자 문장과 스키마로 해석을 재점검한다. 제안 SQL로 사용자의 조건을 역추정하지 않는다. 해석되지 않은 범위/복수 범주 조건은 보존하고 같은 SQL 수정 루프를 반복하지 않는다.
4. 명시적 범주 동등 조건은 capped profile에서 관측되지 않은 값도 허용한다. 같은 컬럼 옆의 `A과 B이고`, `A와 B인`, `A 및 B인`, 쉼표 목록은 IN 조건으로 처리한다. 불완전 목록의 첫 값만 필터로 사용하지 않는다.
5. 한 수치 범위와 상수 범주 조건의 일반 시각화 요청은 스키마를 확인해 분포를 추천하고 빈도 집계를 DB에 보낸다. NULL 제외는 정확히 검증된 빈도 계획/결과/차트에서 일관되게 비교한다.
6. 이전 독립 집계 결과가 여럿 있어도 원본 모집단으로 오인하지 않는다. 정확한 SQL과 일치한 검증 결과만 재사용하고, 조건 변경 시 새 빈도 계획을 만든다. 다른 원본 분기·현재 결과만 분석하는 선택 계약은 유지한다.
7. 재개 시 보강된 scope를 유지하고 소진한 모델 예산을 초기화하지 않는다. 검증된 도구 경로가 있으면 이어서 완료하고, 없으면 구체적 미완료 상태로 종료한다. 완료 시 오래된 scope 오류를 제거한다.

## 실제 검증

| 요청 | MySQL | Databricks | 원본 대신 반환한 빈도 |
|---|---:|---:|---:|
| primary, age 30~40 | 27,439건 | 27,439건 | 11행 |
| primary 또는 secondary, age 30~40 | 208,699건 | 208,699건 | 11행 |

각 DB 검사에서 실제 0행 스키마 조회 1회와 production runtime의 COUNT 조회 1회를 실행했다. 추가 모델 호출 0회이며 PNG 실물이 생성됐다. 합성 회귀는 독립 DuckDB 실행 결과와 비교했고, 실제 DB 두 곳의 동일 건수는 백엔드 일치 근거다. 범용 자유형 모델 계획 성능을 측정한 검사는 아니다.

- 기존 웹 대화의 원래 요청: run `220221d7385041b3acd5e110fb482dd7`, 8.072초, 추가 모델 0회, COUNT 1회. 중간 receipt 검증의 NULL 제외 오거절을 추가로 발견하고 계획/receipt 비교를 수정했다.
- 복수 범주 실패 재개: run `9afd3bbc699946a58c5511ebd2e44b8a`, 8.196초, 추가 모델 0회, COUNT 1회, scope 거절 0회.
- 같은 조건 후속: run `e8e59a667e8e442c8bc1078ba7efd721`, 0.331초, 추가 모델·DB 0회. 같은 이미지와 208,699건을 표시했다.
- 최신 코드 Rerun 뒤 재검증: run `eee4cb04b7e340998a40ad0ca7b8d19a`, 0.502초, 추가 모델·DB 0회. 기존 대화에서 같은 조건과 이미지·208,699건이 유지됐다. [현재 화면](final_followup_web.png).
- 기존 결과와 대화가 보존됐고 원본 행 전체를 새로 로딩하지 않았다. 8504는 로컬 MySQL 평가 서버이며 실제 `.env`의 Databricks 기본 설정은 바꾸지 않았다.

## 이어서 발견한 공통 EDA/메타데이터 문제

원본에 숫자 문자열과 결측이 섞이면 처음에는 범주형으로 분류된다. 숫자 변환 도구가 검증된 numeric child를 만든 뒤에도 이전 bar 계획/원본 ID가 남아 있으면 평균+히스토그램을 완료하지 못했다. 검증된 변환 컬럼과 dtype에 근거하여 histogram 계약을 다시 결합하고 이전 bar 계획은 현재 요청에서 제외했다. 원본·변환 계보·필터·아직 완료하지 않은 평균 목표는 보존한다. 숫자 변환 전에 범주 차트만 만들어 복합 목표를 완료했다고 하지 않는다.

독립 기대 평균·빈도·사용자 지정 bins·변경된 컬럼 이름과 원본 digest를 함께 검사했다. 이 검증은 scripted model 1회와 실제 분석 도구를 사용하는 합성 회귀이며 새 실제 Ollama의 자유형 EDA 성공률로 계산하지 않는다.

또한 명시된 information_schema 출처의 테이블명/타입 목록을 미정 scalar 통계로 오인한 계약을 수정했다. 실제 catalog에 근거한 발견 계획과 execution receipt를 연결해야 목록이 완료된다. 기존 ledger/표시 테스트의 구형 free-form SQL fixture는 도구가 반환한 발견 계획으로 갱신했다. scripted-model 제안 경로는 해당 runtime 인스턴스의 controller 계획만 격리하며 별도 실제 controller/AppTest 경로는 유지한다. 205행 표시 제한 검사는 LIMIT 100 조회에서 205행이 반환됐다고 꾸미지 않고 행 제한 없는 읽기 계획을 사용한다.

원본 두 분기 migration 검사는 실제 needs_context 관찰 두 번 뒤 명시된 나중 snapshot이 선택되는 동작을 검증하도록 관찰 순서를 정정했다. 마지막 선택·parent·원본 보존·원격 0회 검사는 유지했다.

## 회귀 검사와 한계

범위·출처·조건 변경·후속·재시작·잘못된 SQL 거절·원본 보존 관련 검사는 155 PASS, 233 subtests PASS였다. 이어서 복합 EDA/범위/완료 검사 65 PASS·62 subtests, 메타데이터/자동조회/표시 검사 66 PASS·4 subtests, 테스트 격리 수정 검사 46 PASS·2 subtests를 확인했다. 이 수치들은 검사 묶음끼리 겹치므로 합산 점수로 쓰지 않는다.

중간 전체 v6은 26실패/651통과/4skip였다. UUID 범위 오인, 복합 EDA 상태 전이, 메타데이터 요청 분류와 구형 fixture/관찰 순서를 수정했다. 이전 HEAD 의도 파서만 바꿔도 25실패가 재현된 비교는 저장소 전체 이전 revision과의 비교가 아니다.

중간 v7에서는 192실패/538통과/4skip가 나타났다. 테스트 helper를 임시 TestCase로 호출하면서 전역 planner patch cleanup이 누락되어 다른 검사의 로컬 복구까지 꺼진 문제였다. patch를 각 runtime 인스턴스로 제한하고 실제 호출 TestCase의 cleanup을 사용하도록 보정했다. 이 결과를 제품의 192개 독립 결함이나 성공률로 계산하지 않는다. 중간 실패를 숨기지 않고 최종 전체 검사와 분리해 [검증 요약](validation.json)에 기록한다.

최종 v8 전체 `tests migration` 검사는 **671 PASS, 0 FAIL, 4 SKIP, 471 subtests PASS**, 92.25초, exit code 0이었다. Skip은 opt-in MySQL 실DB 통합 4개다. 별도로 `TELLY_TEST_MYSQL=1`을 켜서 실제 MySQL 스키마·읽기·metadata·최신행 histogram·관계·Streamlit 목록/컬럼 후속까지 **4 PASS, 0 FAIL**, 11.84초를 확인했다. 일반 회귀 결과와 실제 DB 검증은 구분한다. `compileall`, `git diff --check`, 현재 서버 health도 성공했다.

일반 Ollama 추론의 60초 지연/timeout, 고급 복합 SQL 및 새로운 schema/표현의 독립 held-out 평가를 해결했다고 주장하지 않는다. 회사 서버의 실제 네트워크·권한도 이번 PC 검증과 별도다. 범용 GO는 NO-GO로 남긴다. 이번 변경은 commit/push하지 않았다.
