# LLM 우선 목표 해석으로 구조 전환

2026-10-05. 대상: `core.analysis_agent.runtime.GraphAnalysisRuntime` 및 실제 Telly/MySQL 개발 웹. 범용 GO 판정이나 Claude Code 수준의 성능 인증은 아니다.

## 바뀐 실행 권위

새 자연어 → LLM 목표 해석 → 구조·대상 바인딩 검증 → 실행 계획/도구 → 관찰/실제 SQL·데이터·PNG 검증 → 완료 또는 남은 목표 복구.

- `intent_mode='llm'`이 제품 기본값이다. UI와 환경 설정에는 규칙 기반 해석으로 돌아가는 옵션을 추가하지 않았다.
- `goal_interpreter.py`: 같은 설정 모델로 현재 원문, 확인된 이전 분석, 별도 스키마 주제, 선택 데이터의 출처/범위, 제한된 카탈로그를 해석한다. Ollama에는 JSON schema·reasoning=false·최대 2048 출력으로 목표만 생성한다. 실행 계획 모델의 기존 설정은 바꾸지 않는다.
- `goal_contract.py` / `goal_options.py`: 모델이 정한 작업·측정 컬럼·조건·출처·재사용/갱신을 실행 계약에 전달한다. 자연어 정규식으로 작업을 재분류하지 않는다. 구조가 틀리거나 현재 결과가 다른 출처이면 모델에 오류를 돌려주고 최대 1회 구조 수정을 요청한다. 실패 시 도구를 실행하거나 완료했다고 주장하지 않는다.
- Recovery는 목표가 확정되기 전 실행을 하지 않는다. 도구가 추가 차트/통계 의무를 만들거나, 숫자 표현 파서가 LLM 조건을 덮어쓰는 경로를 차단했다. 그룹 계산의 그룹 컬럼도 구조화된 목표에서 받는다.
- SQL AST, schema/ID, source/snapshot/coverage/grain, 원본 보존, 원격 receipt, 읽기 전용 정책, 중복 제출 방지, 이미지 검증 및 모델/도구 예산을 유지한다. 출처·조건이 확정된 간단한 계산에는 검증된 로컬 계획을 실행한다.
- UI의 명시적 카드 선택과 정확한 SQL 로딩 이벤트는 구조화된 입력으로 처리한다. 자유 문장 의미를 파싱하는 것과 구분한다.
- 과거 `_state`의 의미 파서는 `_legacy_state`로 분리하고 명시적인 `contract_fixture`에서만 사용한다. 기존 회귀/실행 fixture가 이 모드를 지정하도록 변경했다. 이는 의미 이해 점수가 아니다. 해당 코드를 물리적으로 다른 모듈로 정리하는 작업은 남아 있다.

## 발견한 실패와 수정

처음 실제 모델 4건 중 1건만 완료됐다. 필수 JSON 필드 누락, mode/task 불일치, 요청하지 않은 NULL 조건 추가를 확인했다. JSON schema, 프로토콜 예시, 제약 피드백을 보강했다. 목표의 측정 컬럼을 로컬 실행 계획에 명시해 범위 컬럼과 동일한 측정값이 누락되는 문제도 수정했다.

실제 기존 웹에서는 처음 목표 입력 16,382 bytes가 14,336 보수 예산을 초과해 호출 전에 차단됐다(오류 `5c98b40753a2`). 전체 스키마는 보존하고 모델 뷰는 전역 48개 컬럼/테이블당 최대 8개, 짧은 이전 메시지로 제한했다. 상세 스키마는 `inspect_table_context`로 확인한다. 뒤의 정상 요청 입력은 11,761~12,473 bytes였다. 추정치는 실제 토큰 수와 다르다.

재개에서는 모델이 명시적 stormtrooper 요청을 다른 선택 데이터의 현재 결과로 잘못 해석했다. 데이터가 섞이지는 않았지만 불필요한 질문으로 종료됐다. 현재 결과 출처 불일치를 목표 검증 단계에서 거절하고 모델에 재해석하도록 보강했다. 초기 실패는 삭제하지 않고 증거에 보존했다.

## 검증

### 실제 모델 / 독립 합성값

`gemma4:e4b`, Ollama, 독립적인 20행 합성 raw 데이터. 원격 DB 없음. `live_model_initial.json`, `intermediate_failures.json`, `live_model_final.json`을 분리했다.

| 요청 | 최종 결과 | 목표 모델 호출 | 마지막 측정 시간 |
|---|---|---:|---:|
| observations에서 열 개 행 | 실제 10행 표 | 1 | 9.557초 |
| reading 히스토그램은 그리지 말고 컬럼 목록 | 3개 컬럼, 차트 없음 | 1 | 10.777초 |
| 평균은 계산하지 말고 합계 | SUM=190 | 1 | 11.054초 |
| reading 3~8 합계 | 조건 보존, SUM=33 | 1 | 36.051초 |

4/4은 이 좁은 수용 묶음의 결과다. 광범위한 자연어 성공률·p95·Spider·DeepEval 점수로 확대 해석하지 않는다. 마지막 실행 중 웹 모델 요청도 있었으므로 이 시간은 순수 모델 생성 시간으로 해석하지 않는다.

재실행: `.telly_runtime/v1-venv/bin/python scripts/evaluate_llm_goal.py --output /tmp/telly-goal-evaluation.json`

### 실제 사용자 웹 대화

기존 `0728dee0-d555-4aa2-853b-1101679346da`에서 같은 모델을 호출했다.

| 요청 | 관측된 결과 | 모델 호출 | 추가 데이터 로딩 | 시간 |
|---|---|---:|---:|---:|

DB schema metadata 조회와 분석 원본 데이터 로딩은 구분한다. 35개 기존 자산 metadata/payload 및 20개 Parquet 파일 hash, 선택 ID가 동일하다. 새 원본이나 차트 자산은 추가하지 않았다. 최종 checkpoint는 complete이다. `web_evidence.json`과 `web_rows.png`, `web_context.png` 참조. 파일 hash 기준은 첫 목표 실패 이후 아직 데이터 도구가 실행되지 않은 시점이며, metadata/payload/선택 기준은 첫 재시작 전이다.

## 남은 범위

- 공식 Spider/DeepEval, 미채점 분석 문항, 다회 대화·복잡한 EDA·대형 데이터·고장 주입을 새 LLM 경로로 재평가해야 한다. 예전 규칙 기반 fixture 결과를 새 의도 이해 성적으로 사용하지 않는다.
- 단일 공통 source/scope로 표현할 수 없는 복합 목표, 복잡한 조건/기간/분모/조인 역할과 차트 스타일은 목표 구조 및 독립 oracle 확대가 필요하다. 지원하지 않는 목표를 단순화해 성공으로 처리하지 않는다.
- 예시 카탈로그 밖의 테이블/별칭·넓은 스키마의 의미 탐색, 잘못되었지만 구조적으로 유효한 목표의 의미 정확도, 지속적인 모델 지연 및 엄격한 전체 deadline은 추가 검증 대상이다.
- 운영 Databricks 연결과 회사 서버의 실제 사용자 여정은 이번 MySQL 개발 검증과 별도다. `.env`의 Databricks 기본 설정은 유지했다. commit/push는 수행하지 않았다.

최종 서버: `127.0.0.1:8504`, PID 15962, MySQL 개발 override, health `ok`. 마지막 코드로 재시작 후 기존 최종 응답과 입력창 복원을 확인했다.
