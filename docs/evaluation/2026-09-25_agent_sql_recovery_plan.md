# SQL 분석 agent 실패 해결 설계 (2026-09-25)

상태: **구현 계획, 미완료**. 근거와 NO-GO 판정은 [같은 날의 출시 기록](2026-09-25_go_decision.md)에 있다. 이 문서는 공개 Spider2-Lite `local009`의 실패를 출발점으로 삼지만, 제품 코드는 특정 테이블·컬럼·값에 의존하지 않아야 한다. 별도 서버 배포는 이번 로컬 단일 사용자 범위 밖이다.

## 무엇이 동시에 실패했나

1. `resolve_request_scope()`는 사용자 문장의 OR를 인접한 두 개의 스키마 기반 동등 조건으로 묶지 못하면 `unsupported_disjunction`을 남긴다. `local009`의 출발지/도착지 역할은 조인된 같은 `city` 컬럼의 서로 다른 별칭이므로 현재 `column, op, value`만으로 역할을 구분하기 어렵다.
2. `scope_matches()`는 `single_table(tree)`가 없는 SQL을 거절한다. OR 인식만 수정해도 이 조인·CTE 질의의 범위 증명을 통과시킬 수 없다. 현재 거절은 잘못된 범위의 원격 실행을 막는 안전 동작이며, 검증을 끄거나 이 문항만 예외 처리해서는 안 된다.
3. 모델 초안은 공개 SQLite에서 `no such function: ST_Y`로 실패했다. 모델의 함수·자료형·방언 선택이 틀렸고, 60초 응답 제한에 걸리는 모델도 있었다.
4. Spider adapter는 SQLite 과제를 Databricks 승인 도구에 전달하고 참고 문서를 사용자 메시지 뒤에 덧붙인다. 이는 제품 Databricks 성능과 Spider SQLite SQL 정확성을 혼합하고, 문서의 표현이 사용자 의도 분석에 유입될 수 있다.
5. 범위 거절 후 모델은 수정된 제안을 완료하지 못했다. 범위 불일치를 알리는 일반 문장만으로는 어떤 조인 역할·조건·방언을 고쳐야 하는지 충분히 알려주지 못한다.

## 순서가 있는 수정 작업

### P0. 평가 경계를 먼저 분리

- Spider 전용 adapter에는 `dialect=sqlite`, 공개 읽기 전용 SQLite 스키마, 과제 질문, 과제 참고 문서를 **서로 다른 필드**로 제공한다. 참고 문서는 사용자 요청의 범위 추출 대상이 아니다. 제품 Databricks 경로의 SQL 실행·승인 정책은 그대로 둔다.
- SQL 제안은 사용자의 데이터를 조회하지 않고 공식 공개 SQLite 파일에서만 읽기 전용·시간 제한으로 실제 실행 가능성을 검사한다. `EXPLAIN QUERY PLAN`만으로는 이번 `ST_Y` 오류가 잡히지 않았으므로 이를 실행 검사로 간주하지 않는다. 채점은 공식 Spider evaluator의 EX를 사용한다.
- 평가 결과를 `model_no_output`, `model_timeout`, `scope_unresolved`, `scope_mismatch`, `dialect_error`, `sql_runtime_error`, `wrong_result`, `success`로 구분한다. 제안 없음과 SQL 오답을 같은 점수로 뭉개지 않는다.

### P1. 사용자 요청을 검증 가능한 계약으로 표현

- 질문에서 요청한 데이터 출처, 조인 역할, 컬럼, Boolean 조건식(`AND`/`OR`), 측정값, 단위, 데이터 범위를 구조화한다. 동적으로 읽은 현재 스키마와 관계를 근거로 별칭을 연결한다. 역할이 다른 동일 컬럼은 같은 컬럼명이라는 이유로 합치지 않는다.
- 현재 지원하는 단순 AND/IN/한 OR 그룹은 유지한다. 조인과 CTE는 SQL AST에서 테이블 별칭을 실제 출처에 바인딩한 뒤, 요청의 Boolean 조건과 SQL의 적용 조건이 동치임을 증명할 수 있을 때만 승인 제안으로 넘긴다. 조인 증명이 불가능한 경우에는 `scope_unresolved`와 필요한 스키마/관계 정보를 구체적으로 남기고 멈춘다.
- 스키마 이름이나 특정 도시 값, 예시 SQL을 공통 planner에 하드코딩하지 않는다. 참조 문서·컬럼형·값 인코딩(JSON/좌표 등)은 실행 시점의 컨텍스트에서 찾는다. 질문이 모호하면 사용자에게 의미를 물어야 하며 조용히 조건을 버려서는 안 된다.

### P2. SQL 사전 검증과 복구 루프

- 모델이 SQL을 작성하면 **원격 승인 카드 이전**에 문법, 대상 방언, 현재 스키마의 테이블·컬럼, 허용 함수, 읽기 전용 여부, 출처 계획, 범위 계약을 순서대로 검사한다. 외부 DB에 실제 제출하는 사전 실행은 승인 없이 하지 않는다.
- 거절 시 내부 모델 피드백에 오류 코드, 검증에 실패한 역할/조건, 허용 스키마·함수 요약, 재작성 요구를 구조화해 준다. 같은 SQL 해시의 반복 제출은 중단한다. 재시도 횟수와 시간 예산을 제한하고, 미해결 시 이유와 필요한 다음 행동을 사용자에게 표시한다. 실패 후보나 집계 결과가 보호 원본을 대체하지 않는다.
- 이미 제출됐는지 모르는 Databricks 조회나 거절/실패한 원격 조회는 자동 재실행하지 않는다. 새 SQL이나 재로딩에는 지금처럼 정확한 쿼리 승인 카드가 필요하다.

### P3. 모델 설정은 독립 측정 뒤 선택

- 같은 새 스키마·방언·참고 문서로 모델 **단독** SQL 초안을 여러 번 생성해 실행 가능성·결과 정확도·지연을 잰다. 모델이 정확한 SQL을 안정적으로 만들지 못할 때만 모델 교체, 프롬프트 축소 또는 도구 집중을 선택한다. 한 문항의 단회 결과로 교체하지 않는다.
- 모델이 SQL을 잘 만들어도 agent가 차단하면 P1/P2를 먼저 수정한다. 모델 교체는 범위 검증과 조인 표현 문제를 해결하지 않는다.

## 검증 매트릭스와 완료 조건

| 분리 실험 | 통과 조건 |
|---|---|
| 모델 없이 agent 계약 | 동적 임의 스키마의 올바른 단일 테이블·조인·OR 질의는 승인 제안 단계까지 도달; 조건 누락, OR→AND, 잘못된 조인 역할, 잘못된 범위는 승인 전 거절 |
| agent 없이 모델 SQL | 공개 SQLite에서 읽기 전용 실제 실행 및 독립 정답 비교; 함수/자료형/방언 오류와 60초 초과를 개별 기록 |
| 결합 Spider | 사전에 고정한 5문항과 미관측 다중 스키마 문항에서 SQL 제안률, 공식 EX, p50/p95, 복구 횟수와 중단 이유를 모두 보고. 현재 0/5 제안에서 개선됐다고 주장하려면 동일 분모 재실행이 필요 |
| 제품 Databricks 여정 | 사용자 승인 전 원격 제출 0회; 승인된 정확한 SQL 1회; 보호 원본 불변; 로컬 후속 EDA에는 재조회 0회; 실패·거절·재시작 후 상태와 다음 행동이 명확함 |

모든 안전·보존 반례는 **0건 위반**이 필수다. 자연어/SQL 성공률과 지연의 출시 기준값은 지원 범위와 사용자 요구 성능을 먼저 고정한 뒤, 반복 실측으로 판단한다. 합성 계약 테스트 수나 Spider 한 문항의 성공만으로 GO로 갱신하지 않는다. 구현은 P0→P1→P2→P3 순서이며, 각 단계마다 정상·반례·실제 모델을 따로 평가한다.
