# 로컬 단일 사용자 agent GO 재점검 · 2026-09-26

**판정: 정식 자율 데이터 분석 agent는 NO-GO.** 사용자가 제외한 별도 서버 배포는 판정 범위에서 뺐다. 자동 계약 테스트 통과와 일부 EDA 성공을 실제 모델의 임의 분석·SQL 정확도로 환산하지 않는다.

## 이번에 해결한 경로

- Databricks 모델 serving을 opt-in 모델 공급자로 연결했다. 화면의 모델 선택은 로컬 Ollama를 기본으로 유지하고, Databricks 추론은 토큰 사용량 과금을 명시한다. SQL 데이터 조회 승인 장부는 별도이며 모델 호출이 SQL 재조회 승인을 대신하지 않는다. serving이 거절하는 일부 JSON Schema 키를 모델에 보내기 전에 제거하되 실제 도구 입력 검증은 유지한다.
- 로딩된 raw dataset의 다중 지표 그룹 요약에서 도구 성공 결과를 lineage·snapshot·scope·digest로 검증하고, 완료 근거와 최종 표에 연결했다. 이전에는 계산 도구가 있어도 완료 근거가 없어 반복 한도에 도달할 수 있었다.
- 실제 데이터에서 확인된 두 그룹 값과 단일 수치 집계가 명시된 비교도 구조화된 로컬 집계로 처리한다. 추가 그룹이 있으면 요청한 두 값만 포함하고, 보호 원본을 변경하지 않는다. 테이블·컬럼명과 업무값은 공통 코드에 고정하지 않았다.

## GO로 갱신하기 전에 남은 작업

1. **실제 모델의 다중 스키마 분석 정확성:** 고정 문항과 미관측 문항을 분리해 사용자 의도→동적 스키마 탐색→SQL/로컬 도구 선택→정답/시각화까지 검사한다. 공식 Spider EX, 최종 답변 수치·범위, 실패 이유, p50/p95 지연을 같은 분모로 보고한다. 현재 두 결합 Spider 사례가 실패했으므로 이 문턱을 넘지 못했다.
2. **불명확한 요청의 복구:** 기준일, 모집단, 조인 관계처럼 필수 정보가 없는 경우 사실을 지어내지 않고 필요한 정보를 찾거나 질문한다. 복구 가능한 도구 오류가 나면 제한된 재계획으로 다른 안전한 경로를 시도하고, 정확히 같은 실패를 반복하지 않는다.
3. **실제 웹 사용자 여정:** 새 대화에서 자료 발견·현재 schema 확인·정확한 SQL별 승인 1회·로딩·여러 차례 후속 EDA·차트·실패 후 재개까지 실제 UI로 통과해야 한다. 승인 전/후 원격 제출 수와 보호 원본 digest를 기록한다. 이번 빌드의 기존 표본 후속 그룹 분석 성공은 새 적재를 포함한 전체 여정을 증명하지 않는다.
4. **대용량 지원 범위:** 전체 원본을 로컬로 가져올지 SQL 집계로 처리할지 의도와 데이터 크기에 따라 결정하고, 전송 행 수·메모리·시간 한도를 실측한다. 범위를 넘는 요청은 임의 표본을 전체처럼 답하지 않는다.
5. **사전 합격 기준:** 안전·승인·원본 불변 위반 0건을 필수로 하고, 자연어 성공률과 지연 목표·지원 범위를 평가 전에 확정한다. 목표치가 아직 없으므로 테스트 개수만으로 GO라고 선언할 수 없다.

이번 점검에서는 **새 Databricks SQL 데이터 조회를 실행하지 않았다.** Databricks model serving 호출은 공개 Spider 질문과 합성 데이터에 한정했다.
