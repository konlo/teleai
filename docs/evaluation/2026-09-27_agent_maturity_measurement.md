# 분석 agent 완성도 측정안

작성: 2026-09-27. 기존 [요구·평가 설계](../data_agent_requirements_and_evaluation_2026-09-24.md)의 평가 기준을 구체화한다. 아래 수치는 **제안 기준**이며 이번에 실행한 점수나 새로 확정된 출시 기준이 아니다. 현재 범용 GO 보류 판정은 유지한다.

## 1. 무엇을 성공으로 볼 것인가

한 평가 단위는 사용자의 업무 여정이다. 예: 데이터 탐색 → schema 확인 → 필요한 데이터 로딩 → 평균/분포 → 조건 변경 → 그룹 비교 → 차트 수정 → 원본 범위 복귀. 개별 도구가 성공해도 여정의 필수 요구 하나가 틀리거나 빠지면 전체 성공이 아니다. 부분 달성은 진단용으로 따로 기록한다.

정답 기준은 실행 전에 외부 fixture에 고정한다. 원문 요구, 허용된 모호성 확인, 필수 결과, 금지 동작, 허용 대안, scope/row set, 계산 허용오차, 차트 spec, 데이터 불변 조건, 실행 예산을 포함한다. agent가 해석한 목표 목록을 그대로 평가 기준으로 복사하지 않는다. Gold 결과/SQL은 agent에 제공하지 않는다.

## 2. 핵심 지표와 분모

| 지표 | 정의 | 기준 제안 |
|---|---|---|
| 자율 업무 완료율 | 독립 oracle 전부 충족 + 해결 방법 개입 없이 예산 내 완료 / 실행한 지원 범위 여정 전체 | 핵심 여정 ≥95%, 기능군별 별도 표시 |
| 자율 복구율 | 사전 지정한 복구 가능 장애 뒤 원래 목표를 개입 없이 완료 / 해당 장애가 실제 발생한 여정 전체 | ≥90%; 장애 종류별 별도 표시 |
| 잘못된 완료율 | 완료 선언했으나 필수 oracle 위반 / 완료 선언한 여정 | 검증 표본에서 0건; 한 건도 출시 차단 |
| 요구 충족률 | 충족한 원문 요구 항목 / 전체 필수 요구 항목 | 실패 원인 진단용; 누락을 전체 성공으로 합산 금지 |
| 대화·schema 일반화 | 조건 유지/해제·테이블 전환·미사용 schema의 올바른 완료 / 각 해당 여정 전체 | 핵심 성공률과 분리, 범주별 공개 |
| 데이터 보존·실행 정책 | 원본 훼손, 잘못된 source 교체, 중복 원격 실행, 권한 위반 건수 | 검증 표본 0건; 한 건도 출시 차단 |
| 효율 | 여정별 p50/p95 시간, 모델/도구/SQL 횟수, 전송·읽기 bytes, peak RSS, 비용 | 같은 환경 baseline·업무별 예산과 비교 |
| 평가 커버리지 | 독립 oracle이 있는 항목 / 선언한 지원 범위 항목 | 핵심 여정 100%; 미채점은 통과가 아님 |

업무 의미를 정말 알 수 없는 경우의 적절한 질문, 사용자가 설정한 권한 승인은 디버깅 개입과 구분한다. 정답에 필요한 질문을 하지 않고 임의 처리한 경우는 자율성이 높은 것이 아니다. 답변 불가능·영구 인증 실패·원격 제출 불확실 상태에는 올바른 중단/설명/보존을 별도 평가하며, 이를 성공적인 분석 복구로 세지 않는다.

재실행해서 성공한 것만 골라내지 않는다. 최초 실패, agent 내부 재시도, 개발자가 수정한 뒤 재실행을 각각 기록한다. 사람이 코드를 수정하거나 재개 버튼을 눌러 성공한 것은 무개입 복구가 아니다. 환경 실패도 전체 사용자 경험 성공률에는 포함하고 원인별 보조 통계에서 구분한다.

## 3. 평가 묶음

기존 200문항은 유지하고 독립 oracle이 없는 항목부터 보완한다. 단일 문항을 아래 태그의 복합·후속 여정으로 확장하고, 개발용 회귀와 봉인한 held-out 평가를 분리한다. 같은 질문의 단어만 바꾼 사례는 완전히 새로운 업무로 과대 계산하지 않는다.

- 정상 EDA: 탐색, 수치 변환, 결측 정책, 필터, 그룹 평균, 분포, 차트 설정 변경.
- 복합·대화: 동시에 여러 산출물 요청, 조건 해제, 원본 복귀, 대명사 참조, 대화 중 source 전환.
- 장애: 잘못된 인자/도구, 일시적 timeout, 오래된 schema, 렌더 실패, 메모리 한도, 저장 성공 후 observation 전달 실패.
- schema 일반화: 개발에 쓰지 않은 테이블, 바뀐 컬럼 이름/타입, 반복 테이블 역할, 새 관계, 같은 이름의 다른 source.
- 규모: 1만·10만·100만행 및 실제 지원 한도 근처. 행 수뿐 아니라 넓은 문자열 열·고 cardinality·NULL·편향을 포함. 실제 원격과 합성을 분리하고 cold/warm·재시작·디스크 읽기도 기록.
- 중단/확인: 의미가 불명확한 값, 없는 데이터, 불확실한 원격 제출, 권한 밖 작업. 근거 없는 추측이나 실행이 없는지 확인.

대표 검증 예: “문자열 수치를 결측 정책대로 변환 → 특정 조건 평균과 5 bins 분포 → 그룹별 비교 → 원본으로 복귀.” 중간에 렌더 오류를 주입한다. 독립 정답, 최종 chart spec, 보존 hash, 새 SQL 여부, 미완료 목표를 확인한다. 새로운 표본/스키마에서도 같은 불변 조건을 검사한다.

먼저 핵심 실제 모델 여정을 최소 3회 반복하는 실행안을 권장한다. 반복 횟수 자체가 충분한 증거라는 뜻은 아니다. 여정 수·실행 수·성공/실패 수·신뢰구간을 함께 보고하고 동일 여정의 반복 상관을 고려한다. 수정 후에는 개발용 회귀뿐 아니라 새로운 held-out으로 재평가한다. 표본 0건 오류는 미래 오류 확률 0이라는 뜻이 아니다.

## 4. 세 평가기의 역할

1. **제품 독립 평가기(필수 gate)**: 독립 SQL/Python 계산과 fixture로 수치, 필터, 분모, NULL, 그룹, 날짜, 정밀도를 검사한다. 저장된 chart spec과 렌더 정보 및 실제 웹 표시를 검사한다. 원본 hash·행 수·snapshot/lineage·실행 ledger로 보존/중복을 확인한다. 따옴표나 답변 문체가 자연스러워도 정답 실패는 통과할 수 없다.
2. **Spider 2.0(고급 SQL 별도 평가)**: schema 탐색을 포함한 기업 SQL workflow 능력을 평가한다. 실행한 variant/subset/버전/분모를 기록하고 공식 scorer 결과와 agent가 과잉 차단한 정답을 구분한다. 이 점수만으로 EDA·차트·대화·원본 보존 완성도를 대체하지 않는다. [공식 benchmark](https://spider2-sql.github.io/).
3. **DeepEval(과정과 설명의 보조 평가)**: task completion, tool selection, 인자·실행 과정 및 대화를 평가한다. TaskCompletion은 LLM judge를 사용하며, ToolCorrectness에는 expected tools 기반 비교 등이 있다. 다른 유효한 해결 경로를 감점하지 않도록 도구의 정확한 단일 순서를 정답으로 강제하지 않는다. 설치 버전 지원과 judge 보정을 확인한 후 사용한다. [Task completion](https://deepeval.com/docs/metrics-task-completion), [Tool correctness](https://deepeval.com/docs/metrics-tool-correctness).

DeepEval의 기존 주요 지표 0.8 이상은 보조 기준 초안으로 유지하되 독립 gate를 대체하지 않는다. Judge는 사람 검토한 정상/오답 사례로 보정하고 잘못된 수치·빠진 그룹·5 대신20 bins 같은 의도적 오답을 반드시 실패로 판정하는지 검사한다. 세 평가 점수는 단일 평균으로 합치지 않는다.

## 5. LLM과 agent 원인 분리

동일 fixture·질문·예산으로 진단 비교한다.

- 실제 LLM + 실제 agent: 최종 제품 능력.
- 유효한 도구 계획 대역 + 실제 agent: 의도 삭제·계약/상태/도구 실행 실패 여부. 대역 성공은 실제 agent 자율 계획 점수에 넣지 않는다.
- 다른 LLM + 같은 agent/도구/데이터: 모델에 민감한 실패인지 확인. 다른 모델 성공만으로 agent 결함이 없다고 결론내리지 않는다.
- 장애 없는 실행과 지정 장애 실행: 목표·상태를 유지하며 실패를 복구했는지 비교.

이번 그룹 평균 누락은 모델 호출 0회에서 발생했으므로 agent 경로 결함이다. 기존 공식 정답 SQL이 차단된 경우도 검증 계약의 표현 범위를 점검해야 한다.

## 6. GO 판정과 현재 상태

화면에는 `지원 범위 / oracle 커버리지 / 자율 완료율 / 자율 복구율 / 잘못된 완료 건수 / 원본·실행 정책 위반 / p95·RSS / 미채점 / GO 사유`를 표시한다. 모델·코드·도구 버전과 run ID를 고정한다. 비용/scan 값이 없으면 0 대신 unavailable로 표시한다.

GO는 사전에 선언한 지원 범위에서 판단한다. 중요한 요구 누락·거짓 완료·원본 유실·중복 실행이 남으면 평균 점수가 높아도 NO-GO다. 범위 밖 고급 SQL 실패는 별도 점수와 명확한 제한으로 관리할 수 있지만, 사후에 실패 사례만 범위 밖으로 빼는 것은 허용하지 않는다.

현재는 최신 감사의 잘못된 완료 2건이 있고, 기존 고정 200문항에는 103 미채점, 고급 SQL은 제한된 5문항 근거만 있다. 따라서 “완성도 90%” 같은 숫자는 산출할 수 없다. 기존 계약 테스트 32개 통과도 이를 대신하지 않는다. [실패 근거](2026-09-27_agent_self_recovery_audit.md).

다음 실행 단위는 **핵심 여정별 외부 oracle 고정 → P0 실패 수정 → 고정/held-out/장애 평가 → 동일 지표 보고**다. 이 문서는 그 측정 계약 제안이며 이번 요청에서 새로운 평가 실행이나 코드 수정은 하지 않았다.
