# 자연어 의도 분기 구조 전수 점검

2026-10-05. 사용자 요청: 자연어를 LLM 대신 프로그램 규칙으로 분기하는 부분의 전체 범위와 심각성을 확인한다.

## 결론

현재 실행 경로는 LangChain/LangGraph agent loop를 가지고 있으나, 그 앞에서 큰 규칙 기반 해석기가 사용자 목표·조건·완료 계약을 만들고 도구까지 먼저 선택한다. **새 자연어 요청을 LLM이 해석하고 계획하는 구조를 일관되게 보장하지 않는다.** 사용자가 요구한 일반적인 데이터 분석 agent의 핵심 요구사항에 대한 P0 구조 결함이다.

앞선 `10개 row`/`row 10개` 패치는 특정 표현의 실패를 막았으나 이 원인을 해결하지 못했다. 모델 호출 0회·빠른 처리·계약 테스트 통과를 자연어 이해나 agent 완성도의 증거로 제시해서는 안 된다.

## 점검 범위와 수치

실제 활성 경로: `pages/Telly.py` → `ui/analysis_page.py` → `GraphAnalysisRuntime` → `create_agent` middleware. 구형 `core/chat_flow.py` → `utils/chatbot_plan.py` 경로는 현재 웹의 주 실행 경로와 구분했다.

AST로 production `core`, `utils`, `ui`, `pages`의 Python **128개 파일**을 검사했다. 테스트·스크립트·외부 패키지는 이 수치에서 제외했다.

| 측정 | 수치 | 해석 |
| --- | ---: | --- |
| 전체 정규식 호출 지점 | 322곳 / 37파일 | SQL·타입·보안·로그 처리와 구형 경로 포함 |
| 현재 agent 폴더 | 270곳 / 25파일 | 자연어 해석 외 검증 코드도 포함 |

| intent_scope.py | 37곳 | 필터·범위·참조·분모 등의 의미 파싱과 검증 혼재 |

`_state`는 1,797줄, if 노드 318개다. `_next_local`은 1,123줄, if 노드 215개다. if 개수는 상태·증거 처리도 포함하므로 자연어 분기 개수로 해석하지 않는다.

## 실제 제어 흐름

1. `runtime.py:150`의 RecoveryPlanningMiddleware가 요약/모델 추론보다 먼저 호출된다.
2. `recovery.py:195`의 `_state`가 원문에서 의미 플래그·출처·조건을 만든다.
3. `before_step` 마지막에서 `_next_local`이 호출된다(`recovery.py:4120` 부근).
4. 규칙에 맞으면 프로그램이 AI tool call을 작성하고 `jump_to='tools'`로 이동한다. 모델은 이 새 요청을 읽지 않을 수 있다.
5. 프로그램 해석과 일치하는 결과가 나오면 완료 계약을 만족해 모델 없이 종료할 수 있다.
6. 로컬 분기를 타지 않은 경우에는 일반 LLM 도구 호출이 존재한다. 그러나 모델 메뉴·시스템 지시·SQL 검증도 앞에서 만든 플래그와 조건을 사용한다. 잘못된 해석은 이 경로에서도 영향을 준다.

LangGraph를 사용한다는 사실만으로 의도 이해가 LLM 중심이 되는 것은 아니다.

## 격리 재현: 새로 확인한 3개 잘못된 선행 분기

실제 production `_state`와 `before_step`을 임시 저장소·일반 synthetic schema로 호출했다. 모델은 NoInference, SQL 실행기는 연결하지 않았다. 사용자 대화·DB·8504 서버에는 새 요청을 보내거나 상태를 변경하지 않았다. 결과는 `probes.json`에 저장했다.

| 요청 | 요청 의미 | LLM 이전 결정 |
| --- | --- | --- |
| `observations table row 10개 보여주지 말고 테이블 목록만 보여줘` | 목록만 | row_preview limit=10, prepare_row_preview 도구로 이동 |
| `reading 히스토그램은 그리지 말고 컬럼 목록만 보여줘` | 컬럼만 | kind=histogram, prepare_histogram 도구로 이동 |
| `reading 평균은 계산하지 말고 합계만 알려줘` | SUM만 | operations=[AVG,SUM], local_analysis_sql 도구로 이동 |

이 세 경우는 **잘못된 해석 및 도구 선택** 재현이다. 실 DB 결과나 전체 턴 최종 답변까지 실행한 테스트로 계산하지 않는다.

추가로 `열 개 행`, `Give me ten records`, `처음 열 줄`은 row_preview가 인식하지 않았고 모델 경로로 남았다. 이것만으로 최종 실패를 단정하지 않는다. 같은 뜻이 표현에 따라 다른 해석 경로를 거친다는 증거다. `분포를 설명만 하지 말고 그려줘`는 chart=true이나 종류는 미확정이었다. 이 경우 역시 최종 실행 결과는 미검증이다.

## 주요 구조 결함

1. **P0 — 선행 규칙 해석이 실행 권한을 가짐.** 부정·정정·복합 문장의 의미를 모델이 판단하기 전에 도구 실행과 완료 계약이 확정된다.
2. **P0 — 의미 검증의 기준도 같은 파서.** `intent_scope`가 만든 조건을 `_proposed_scope_valid`와 완료 검증이 정답으로 사용한다. 결과가 프로그램 계획과 같다는 검증은 원래 사용자 의도와 같다는 증명이 아니다. 정상 SQL의 잘못된 거절과 엉뚱한 완료 모두 가능하다.
3. **P1 — 좁은 의미 resolver가 일반 요청 해석을 대체하지 못함.** semantic.py는 조건이 제한된 COUNT/AVG 대상 바인딩, operation_binding.py는 이미 확인한 한 컬럼의 단일 AVG/MEDIAN/MIN/MAX/SUM에 한정된다. 승인 대기 문장 분류도 별도 LLM 경로가 있으나 일반 계획자는 아니다. 프로그램이 잘못 인식한 기존 연산이 있으면 operation resolver 후보에서도 빠질 수 있다.
4. **P1 — 도구 메뉴가 잘못된 분류에 종속.** tool_focus.py, model_context.py GROUPS가 파서 플래그로 노출 도구와 지시를 제한한다. 설명 전용 분류는 도구를 0개로 만든다. search_analysis_tools 탈출구는 존재하지만 모델 이전 강제 분기에는 도움이 되지 않는다.
5. **P1 — 테스트 수와 자연어 품질의 혼동.** test_row_preview 등은 NoInference로 모델 없이 완료를 요구하고, test_actual_agent_evaluation은 scripted model이다. 이런 검사는 실행·자산·계약 검증에 필요하지만 사용자 표현 이해의 증거가 아니다. 실제 모델 평가 스크립트도 존재하므로 모든 평가가 가짜라고 단정하지 않는다. 다만 최신 733 PASS만으로 이 구조적 요구를 검증하지 못하며, 이번 3개 선행 분기 결함이 남아 있다.

## 전환 요구사항

**새 자연어 발화 → LLM 목표 해석/계획 → 프로그램의 사실·정책 검증 → 도구 실행 → 관찰 → LLM 재계획 → 결과 계약 검증**으로 역할을 분리한다.

- 새 자연어 요청은 원문과 확정 대화 상태를 모델에 전달해 목표/변경사항을 먼저 해석한다. UI의 정확한 dataset/chart ID 선택, 승인 버튼, 중단 버튼은 구조화된 이벤트이므로 자연어 해석 대상에서 제외할 수 있다.
- 해석은 버전 있는 구조화된 목표로 저장한다: 대상·출처·컬럼 역할·조건 트리·모집단/분모·행 선택 순서·정렬/NULL/동률·차트·새 요청/수정/취소·모호성. 모델은 확인되지 않은 컬럼을 발견 도구로 조회할 수 있어야 한다. 고정된 하나의 intent enum으로 자유 계획 능력을 제한하지 않는다.
- regex는 숫자/SQL 문법 파싱과 **후보 증거** 제공에만 사용한다. 후보 해석이 목표를 덮어쓰거나 SQL/차트를 직접 실행하지 못하게 한다.
- DB·schema·ID·SQL AST·읽기 정책·메모리/행/시간 한도·원본 불변성·receipt·PNG 검증은 프로그램에 남긴다. 의미 모호성은 새로운 도구 관찰/모델 재판단으로 돌리고, 결정적 실행 오류는 한도 내 수정한다.
- 프로그램은 이미 확정된 계획의 query→저장→render, 정확한 receipt 재사용 등을 모델 호출 없이 이어갈 수 있다. **사용자 의미를 새로 결정하는 것**과 **확정된 계획의 기계적 실행**을 구분한다.
- 계획 해석과 SQL/도구 검증이 충돌하면 원문·확정 목표·충돌 필드를 함께 모델에 돌린다. 파서에 새 표현을 추가하거나 의미 검증을 꺼서 해결하지 않는다.
- 완료 검증은 최초 목표와 최신 사용자 수정사항으로부터 만든 의무를 기준으로 해야 한다. 실행자가 자기 계획으로 완료 의무를 바꿀 수 없게 한다. 복합 요청의 일부만 완료하면 부분 완료로 표시한다.
- 진단 로그에 interpreter_origin, goal_version, plan_version, 원문 근거 위치, 충돌 필드, 모델 이전 controller 실행 사유를 추가한다. 실제 데이터/원문/토큰을 공개 진단에 불필요하게 노출하지 않는다.

평가를 먼저 고정한다: 어순·한글/영어 숫자·부정·조건 수정·주제 전환·생략·복합 요청·schema 변화·큰 데이터 재사용·도구 실패 후 대안. 독립 기대 목표/조건/도구 효과와 실제 결과를 비교한다. 같은 파서에서 기대값을 생성하지 않는다. 목표 해석 정확도, 불필요 SQL, 원본 보존, 조건/모집단 일치, 복구 성공, 실제 이미지, p95 시간/모델 호출을 별도 측정한다. deepEval 심사 점수와 Spider SQL 실행 점수만으로 대화·로딩·시각화까지 완료됐다고 판정하지 않는다.

이번 턴은 **진단·격리 재현·전환 요구사항 정리**다. 제품 코드를 이 구조로 전환하거나 새 모델 평가를 실행하지 않았다. 기존 서버는 유지했고 범용 GO 판정을 하지 않는다.
