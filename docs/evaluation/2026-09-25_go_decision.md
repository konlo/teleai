## 출시 차단 이유와 재판정 조건

1. **새로운 분석 과제의 자율 해결 실패.** 동적으로 읽은 Spider SQLite 스키마와 과제 참고 문서가 있어도 SQL 계획을 제안하지 못했다. 모델 호출과 재계획의 시간·도구 관찰을 개선하고, 결과를 보지 않은 공개 held-out 문제에서 SQL 제안→공식 evaluator 실행→정답을 확인해야 한다. 점수 분모와 지연 기준을 출시 범위에 맞게 먼저 고정한다.
2. **요청한 수치의 최종 답변 누락.** 구조화 계산이 성공해도 Q1·Q3·IQR을 답변에 넣지 않았다. 계획의 필수 산출물과 최종 표현의 대응을 검증하고, 같은 유형 및 반례에서 누락·허위 완료가 없는지 반복 검사해야 한다.
3. **실패 턴의 재개 한계.** 실제 웹에서 중앙값 요청이 모델 지연으로 267.204초 후 `ReadTimeout`이 났다. 이후 정확한 10,000행 표본 선택을 수정해 새 턴은 0.283초/모델 0회로 성공했지만, 이미 실패한 턴의 `미완료 분석 재개`는 반복 한도를 이어받아 `exhausted`로 종료됐다. 새 요청 재입력 없이 복구되는지 검증해야 한다.
4. **대규모 전체 분석 범위 미검증.** 실제 웹은 10,000행 제한 표본, 합성 저장 시험은 75만 행·5열이다. 전체 테이블을 다루는 streaming/부분 scan, Databricks 집계 선택, scan·전송·RSS·시간 예산은 이 결과로 보증할 수 없다. 지원 범위를 표본 기반 EDA로 축소하거나 별도 대규모 실행 경로와 실측 합격 기준을 마련해야 한다.

다음 재판정에는 위 차단 항목을 같은 고정 문항·신규 held-out 문항·실제 웹 대화에서 모두 검증해야 한다. 승인 없이 원격 Databricks 데이터를 다시 로딩하는 검사는 수행하지 않는다.
