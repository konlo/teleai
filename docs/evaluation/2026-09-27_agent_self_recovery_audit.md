- 전체 요청·분류 상태·도구·독립 oracle·결과: [JSON 증거](2026-09-27_numeric_continuation_audit.json)

## 보강 우선순위와 코드 근거

### P0-1. 분석 목표와 데이터 처리 조건을 별도로 보존

`core/analysis_agent/recovery.py:325`는 차트가 없는 요청에 `결측/missing`이 있으면 `profile_kind=missing`으로 분류한다. `:550`에서 그 결과가 `calculation=False`, `operations=[]`로 평균 목표를 지운다. “결측을 어떻게 처리할지”라는 부가 조건을 “결측 현황을 보여달라”는 주 목표로 바꾼 것이다. 새 그룹 평균 재현에서는 모델 호출 전에 이 경로로 종료됐다. **이 사례는 LLM 품질 문제가 아니라 agent 의도 결합 문제다.**

보강: 원문에서 `목표[]`, `필터`, `그룹`, `지표`, `결측 정책`, `차트 설정`, `데이터 출처/범위`를 독립적으로 유지한다. capability 선택이 기존 목표를 삭제하지 못하게 한다. 파싱이 불확실하면 근거 확인/의미 해석으로 넘기고 다른 작업을 완료했다고 처리하지 않는다.

완료 기준: 그룹 평균+결측 변환/결측 제외/결측 유지/결측 현황도 함께 요청한 조합을 서로 구분한다. 새로운 테이블·컬럼과 한·영 표현에서도 실제 그룹별 정답이 있어야 완료된다.

### P0-2. 이미지 존재와 요청한 시각화의 충족을 구분

`recovery.py:236`의 chart 설정 인식은 `5개 구간` 등 특정 표현에 의존한다. 이번 “구간 수 5개”는 `chart_spec_requested=False`로 분류됐고 기본 20 bins가 사용됐다. `completion.py`의 chart 완료 계약은 앞 단계에서 채택된 artifact를 요구하지만, 앞 단계에서 누락된 설정까지 복원하지 못한다.

보강: 요청한 chart spec을 별도 계약으로 저장하고 도구가 반환한 `chart_spec`과 실제 렌더 결과를 비교한다. 축·구간·그룹·정렬·필터를 충족하지 않은 이미지는 완료 근거가 될 수 없다. 필요한 설정을 지원하지 못하면 제한을 알리고 가능한 대안을 제시한다.

완료 기준: `구간 수 5개`, `5개 구간`, `bins=5`를 동등하게 검사하고, 5 대신 20으로 렌더한 결과는 의도적으로 차단한다. 차트의 존재만 검사하는 회귀로 대체하지 않는다.

### P0-3. 복잡한 SQL의 요청 계약·검증 피드백·재계획을 함께 확장

이전 실제 모델 Spider2-Lite 고정 5문항에서는 SQL 제안 1/5, 공식 채점된 제안 정답 0/1이었다. 차단된 초안 중 `local009`는 공식 정답인데 agent의 `request_scope_unresolved`로 차단됐다. 다른 문항에는 홈/원정 한쪽 누락, 요청하지 않은 연도 추가, DISTINCT 고객/중앙값 단계 누락이 있었다. [개별 원인과 score](2026-09-27_advanced_scale/spider_score_summary.json). 이 결과는 최신 수치 변환 수정 뒤 재실행하지 않았으며 전체 Spider 547문항 점수가 아니다.

`analysis_relationships.py:156`의 metadata 기반 보완 경로는 제한된 inner join tree만 처리하며 반복 테이블 역할, CTE/하위 SELECT 등을 제외한다. `recovery.py:3298`의 scope 거절 피드백은 오류·미확정 조건·컬럼·거절 SQL과 재작성 지침을 주지만, 기대 의미와 실제 계획의 차이를 충분히 구조화하지 않는다. 검증기가 표현하지 못하는 의미를 모델에 반복 재작성시켜도 해결되지 않을 수 있다.

보강: 독립적인 요청 계약에 역할별 출처, OR/NULL, 시간 기준, 집계 단위·분모·DISTINCT, 단계별 결과를 표현한다. 검증기는 `잘못된 계획`과 `검증 기능 미지원`을 구분하고 누락된 조건/역할/단계를 반환한다. planner는 그 차이를 해결할 수 있는 단계만 다시 계획한다. **검증기를 끄거나 정답 SQL을 무조건 통과시키는 방식은 금지한다.**

완료 기준: 기존 5문항의 최초 실패를 보존하며 동일 schema의 held-out 변형을 추가한다. 정답 과잉 차단과 의미상 오답 허용을 별도로 측정한다. 특정 질문/테이블용 SQL 하드코딩은 허용하지 않는다.

### P1-1. 변환→필터→집계→차트를 조합 가능한 실행 단계로 연결

`recovery.py:2069`의 준비된 numeric branch 직접 continuation은 필터·grouping·명시적 chart 설정이 있으면 제외된다. 다른 로컬 경로가 필터 평균을 계산할 수는 있지만, 이번 재현처럼 남은 차트까지 이어지는 보장은 없다. 숫자 변환 도구 자체도 선택한 수치 컬럼만 보존한 projection이므로 그룹 키가 필요한 후속 작업에는 입력 artifact 계약을 함께 설계해야 한다.

보강: 단계마다 입력 artifact, 필요한 컬럼/그룹 키, 동일 snapshot·행 범위, 출력 schema와 검증 조건을 저장한다. 완료된 평균은 재사용하고, 남은 차트만 같은 필터 branch에서 수행한다. 모델 장애·도구 오류가 발생하면 호환 가능한 대체 단계를 선택한다. 무조건 재로딩이나 처음부터 재실행하지 않는다.

완료 기준: 수치 변환→필터→그룹 집계→복수 차트의 각 경계에 장애를 주입해 최종 결과와 원본 보존, 재실행 횟수, 미완료 목표를 검사한다. 실제 모델 추가 추론으로 복구하는 경우와 모델 없이 이어가는 경우를 따로 측정한다.

### P1-2. 대규모 재사용과 저장된 성공 결과 복구의 비용을 줄임

`utils/analysis_numeric.py:17`은 컬럼을 읽고 전체 변환·검사를 수행한 뒤 `:50`에서 기존 child 재사용 여부를 확인한다. 동일 변환을 반복해도 새 dataset 등록만 피하고 scan 비용은 다시 발생한다. 이는 코드로 확인한 개선점이며 이번 감사에서 대용량 성능을 재측정한 것은 아니다.

또한 `runtime.py:407`의 completed receipt 복원은 `resume()`에서 수행한다. UI `ui/analysis_page.py:199`는 사용자 재개 버튼으로 이를 호출한다. 기존 잘못된 observation에 대한 안전한 복구 경로는 있지만 모든 예외 뒤 자동 reconciliation되는 것은 아니다. 현재 typed JSON 수정으로 해당 신규 직렬화 오류는 방지되어 있으므로 이를 미수정 재현 오류로 주장하지 않는다.

보강: immutable snapshot·변환 정책·입출력 schema로 검증한 캐시를 변환 전에 조회하고 audit 정보를 함께 재사용한다. 실행 성공 receipt와 저장된 artifact가 정확히 일치할 때만 같은 요청 안에서 제한적으로 복원한다. `uncertain` 제출은 자동 재실행하지 않는다.

완료 기준: 동일 변환 재요청에서 불필요한 projection/변환 호출이 없고, snapshot/정책 변경 시 재검증한다. “원격 실행 완료→전달 실패” 장애에서 SQL 1회·원본 유지·정확한 결과 복원을 검증한다.

## 이미 보강되어 있는 부분

- 오류 종류별 대체 도구 안내, 도구 schema 검색, 동일 실패와 무진전 탐색 반복 방지가 있다. `tool_repair.py`는 구조화된 오류 코드에 따라 복구 지침을 생성한다.
- 일부 일시적 모델 장애에서 검증된 로컬 작업을 이어가는 경로, 영속 checkpoint, 원격 중복 제출 방지가 있다.
- 실제 100,000행 저장·원본 보존·평균/필터/차트/재시작 및 단순 수치 변환 복합 요청의 실제 모델 성공 근거가 있다. [직전 보고](2026-09-27_advanced_scale/warehouse_agent_repair.md).

따라서 “agent 기능이 없다”는 진단은 틀리다. **지원되는 개별 경로의 복구는 있지만, 복합 요청 전체를 보존하고 조합해서 완료하는 보장이 부족하다**는 것이 이번 결론이다.

## 일괄 개선·평가 순서

1. 위 실패를 먼저 독립 acceptance로 고정한다. 원문 목표 누락·잘못된 완료는 P0다.
2. 요청 계약 → 단계별 artifact 계획 → 기대/실제 차이 진단 → 미완료 단계 재계획 → 최종 계약 검증을 하나의 흐름으로 보강한다. 기존 데이터 보존/승인/중복 실행 guard는 유지한다.
3. 고정 실패 회귀, 새로운 스키마/표현의 held-out 조합, 단계별 장애 주입, 실제 Databricks 모델·저장된 데이터·웹 여정을 실행한다.
4. DeepEval의 설명 품질과 별도로 독립 수치/SQL 실행 정답·차트 설정·원본 보존을 필수 gate로 둔다. Spider는 실제로 평가한 subset 분모만 표시한다.
5. `자율 복구율`은 실행 중 코드 수정·수동 재개 없이 원래 목표를 완료한 경우만 센다. 잘못된 완료율, 불필요한 SQL 횟수, 반복 호출, p95 시간/RSS도 함께 보고한다. 정답이 없는 사례는 미채점으로 남긴다.

현재 32개 계약의 통과는 위 새 P0를 상쇄하지 않는다. 일반 GO를 선언할 근거는 아직 없다.
