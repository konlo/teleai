# 10행 표 이후 산점도 오류: 원인·수정·설계 평가

2026-10-03. 기존 웹 대화 `0728dee0-d555-4aa2-853b-1101679346da`에서 사용자가 `age를 x축으로 하고 balance를 Y축으로 하는 scatter plot를 그려줘`를 요청한 실패를 조사했다. 기존 데이터와 선택 기준을 보존했다. 이번 변경은 커밋·push하지 않았다.

## 실제 실패 원인

Databricks나 MySQL SQL 실패가 아니다. 해당 산점도 실행의 원격 도구 시작은 0회였다. 모델도 적절한 raw 10행 dataset과 두 축을 골랐고 PNG 생성 도구는 성공했다. 따라서 이번 사건을 “LLM이 산점도를 이해하지 못했다”로 설명할 수 없다.

agent가 직전 10행 표의 표시 범위를 다음 산점도의 분석 범위로 결합하지 못했다. 분석 기준으로 선택된 dataset은 이전의 필터별 빈도 집계였다. 표 표시가 이를 덮어쓰지 않는 것은 올바르지만, 표시한 표의 별도 dataset을 후속 시각화의 참조로 연결하는 계약이 없었다.

도구 실행 전 검증은 조건이 없으면 허용했고, 완료 검증은 전체 데이터가 아닌 raw 10행 결과를 거절했다. 같은 결과에 대해 검증 기준이 달라, 생성된 PNG가 최종 증거로 채택되지 않았다. 이후 불필요한 요약·추론으로 시간 예산을 소진했다. 이미 만들어진 PNG로 완료할 수 있는데도 재개가 모델 단계로 돌아가는 결함도 있었다.

최초 실행 `21336c749f6147e991da43ecf7d9429a`는 209.617초 후 미완료. 모델 예산 오류 `6207538786e3` 이후 사용자가 재요청했을 때 미완료 checkpoint 차단이 일반 ValueError `9698239eabcd`로 기록되어 최초 원인이 가려졌다. 단계별 실제 로그는 [web.json](web.json)에 보존했다.

## 구현한 공통 기능

- `core/analysis_agent/chart_binding.py`에 표시 증거와 축 역할 결합을 분리했다. 실제 dataset ID·출처·snapshot·컬럼·행 수를 검증하고, UI에서 다른 분석 기준을 선택하면 이전 표시 근거를 상속하지 않는다. 특정 테이블/컬럼을 제품 코드에 넣지 않았다.
- 저장된 10행 표 이후 row-level scatter 요청을 같은 10행에 결합한다. 반복 요청과 축 순서 교체도 schema 나열 순서와 구분한다. 전체 모집단·fresh·다른 출처·새 조건·stale 증거에는 이 결합을 적용하지 않는다.
- 산점도 실행 전과 완료 검증에 축과 raw 데이터 범위 검증을 적용한다. 일부 데이터는 명시적인 현재 결과 또는 검증된 표시 근거가 있어야 사용할 수 있다.
- 이미 처리한 tool observation도 표시 근거가 새로 확정되면 PNG 증거를 재검증한다. 도구를 재실행하거나 실패 관찰 횟수를 다시 증가시키지 않는다.
- runtime에 공통 저장 증거 완료 전이를 추가했다. 안전한 model checkpoint에서만 검증된 계약을 완료한다. 수동 재개, 실패한 추론 이후 로컬 완료, 동일 요청 재제출에 적용하며 원격 제출 상태 불명확·승인 대기·tools checkpoint를 자동 재실행하지 않는다. 예산을 초기화하지 않는다.

## 작업 중 추가로 관측한 자연어 실패

웹에서 사용자가 새로 입력한 `age와 balance의 관계를 그려줘봐` 요청도 관측했다. 실행 `00683ff8e3544044a5224f260a28614e`는 ReadTimeout `8ba14bb31264`로 121.350초 후 중단했다. 이 경우 의도 상태가 `chart=False, calculation=True, kind=None`였고 실제 도구는 실행되지 않았다. 즉 모델 지연은 실제 발생했지만, “관계를 그려”라는 시각화 목적을 agent가 잡지 못해 로컬 처리 경로도 놓쳤다.

같은 표시 근거가 있고 요청한 두 컬럼이 실제 데이터에서 수치 타입이면 row-level 관계 시각화에 scatter를 추천하도록 보강했다. 이는 특정 컬럼 예외가 아니며, 범주형 컬럼·통계 연산·불명확한 출처·새 조건은 이 추천으로 바꾸지 않는다. 해당 표현을 외부 fixture와 두 dialect 여정에 추가했다. 아직 모든 자연어 표현의 일반화를 증명하지 않는다.

## 테스트가 왜 놓쳤나

기존 산점도 테스트는 완전한 raw dataset에서 시작했다. 표 테스트는 표 표시 자체에서 끝났다. 각 기능의 통과가 `집계 선택 → 별도 raw LIMIT 표 → 후속 산점도 → 완료 → 반복 → 재시작` 조합의 통과를 보장하지 않았다.

새 테스트는 외부 fixture를 사용해 이 전체 여정, 두 SQL dialect, 축 교체, 원본 digest·선택 보존, 저장 PNG 이후 모델 예산 소진/재시작과 이미 processed된 관찰 복구, 잘못된 출처·snapshot·전체 범위·조건·UI 선택의 차단을 검증한다. NoInference 모델은 추론 의존이 다시 생기면 실패시키는 계약 검증용이며 자연어 LLM 품질 점수로 계산하지 않는다. 실제 Streamlit AppTest에서도 이미지 URL과 완료 상태를 확인했다.

- 관계 표현의 실제 웹 복구 후 새 요청: 0.738초, 모델0·추가 SQL0. 최종 화면에는 age(x)·balance(y)의 10좌표 산점도와 완료 답변이 있으며 미완료 재개 버튼은 없다.
- 기존 웹 미완료 작업: 저장된 PNG를 그대로 사용해 0.023초에 완료. 추가 SQL·모델·그림 생성 0회. 반복 요청에서도 같은 10행의 산점도가 화면과 최종 답변에 표시되었다. [웹 증거](web.json), [화면](final_web.png).
- MySQL 실제 `LIMIT 10`: 10행18열. 후속 scatter 8.304초(전체 회귀 동시 실행), 모델0·추가 SQL0.
- Databricks 실제 `LIMIT 10`: 10행18열. 후속 scatter 0.370초, 모델0·추가 SQL0. 반복 표 조회도 양쪽 SQL0. [실제 양 DB 결과](live.json).
- 최종 전체 회귀 695 PASS / 0 FAIL / 4 SKIP, 491 subtests PASS (144.64초). 중간 실패도 [validation.json](validation.json)에 기록했다. 테스트 수 자체를 운영 GO 근거로 사용하지 않는다.

## 설계상 남은 문제와 개선 우선순위

1. **상태 책임 집중**: recovery의 큰 함수와 여러 dict 키에 의도·범위·계획·도구 관찰·완료가 집중되어 변경 간 충돌을 찾기 어렵다. 기존 [분리 점검](../2026-10-03_modularity/report.md)의 typed 목표/데이터 참조와 capability handler 분리, 계층·복잡도 CI 규칙 적용이 남아 있다. 이번 기능은 별도 모듈로 분리했지만 전체 분리가 끝난 것은 아니다.
2. **계약 일치**: 이번 산점도 입력과 완료를 맞췄지만 모든 도구가 하나의 검증 계약을 공유하는 것은 아니다. 지원 capability별 입력 적합성·출력 증거·완료 기준을 같은 handler에서 관리하고 교차 계약 검증을 확대해야 한다.
3. **평가 단위**: 고립 테스트 통과를 기본 분석 준비 완료라고 안내하면 안 된다. 배포 gate에는 schema 탐색·raw/집계 교차·새 범위·후속 차트 변경·실패와 재시작을 조합한 사용자 여정의 결과를 별도로 표시해야 한다. held-out 자연어·실모델 평가도 별도 유지한다.
4. **부분 범위 일반화**: 이번 자동 표시 결합은 표시된 행이 저장 asset 전체인 경우의 row-level scatter다. 큰 asset 중 일부 행만 표시한 표를 후속 그림에 사용하려면 bounded 파생 dataset을 명시적으로 만들고 표시 범위를 연결해야 한다. 이를 무조건 큰 원본 전체로 바꾸지 않는다. 복합 필터·다른 chart 종류의 표시 참조도 추가 검증 대상이다.
5. **실패 전달**: 한 턴의 최초 모델/계약 오류와 이후 재제출 차단을 연결해 진단해야 한다. 이번 유효한 저장 결과는 새 요청/재개 시 완료할 수 있게 했지만, 근거 없는 미완료 작업을 임의로 성공 처리하지 않는다.

이번 산점도 여정은 수정·검증했다. 범용 자율 분석 agent 전체의 GO 판정은 하지 않는다. 회사 서버는 접속 검증하지 않았으므로 최신 코드 업데이트와 동일 여정의 확인이 필요하다.
