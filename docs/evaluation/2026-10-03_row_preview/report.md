# 10행 표 미리보기 실패 수정 — 2026-10-03

## 실제 실패

- 대화 `0728dee0-d555-4aa2-853b-1101679346da`의 마지막 요청은 `데이타 10개 row만 추출해서 table로 보여줘`였다.
- run `60fc1d254f724497b4899b057e976110`: 모델 ReadTimeout 및 재시도 후 78.759초. 도구 실행·SQL 실행·새 데이터 저장이 없는데 빈 응답을 complete로 처리했다. 화면에는 요청과 이전 age 차트만 남았다.
- 원인은 행 표 미리보기의 의도→계획→실행→표 표시 계약 누락과 빈 답변 완료 허용이다. DB에 SQL을 제출한 뒤 반환되지 않은 사례가 아니다.

## 변경한 계약

- 테이블/컬럼 이름을 하드코딩하지 않고 관측한 schema와 최근 확정 출처에 요청을 연결한다. 생략한 테이블이 모호하면 질문한다. 숫자 행 요청은 1~200행으로 제한한다.
- `prepare_row_preview` 도구를 등록했다. 원본 raw의 전체 컬럼·출처·SQL 계보가 맞으면 파일의 제한된 prefix만 읽는다. aggregate 결과를 raw 행으로 대체하지 않는다. 사용자가 현재 결과를 명시했을 때는 그 결과를 제한된 행수로 표시한다.
- 원본이 없으면 `SELECT * ... LIMIT N` 읽기 계획을 만들고 기존 SQL 검증·연결·실행 정책을 통과해 실행한다. 실제 반환 receipt·출처·행수·snapshot·컬럼을 검증한 뒤 구조화된 표 표시 근거를 저장한다.
- 행 미리보기는 새로운 분석 기준을 선택하지 않는다. 기존 필터 집계·원본·차트·선택 결과를 보존한다. 같은 요청은 저장된 LIMIT 결과를 재사용한다.
- native `st.dataframe`으로 실제 표를 표시하고, 최신 표 아래 오래된 선택 차트를 다시 붙이지 않는다. 빈 일반 응답도 성공 처리하지 않는다. 원본·DB 연결이 모두 없으면 연결 부재를 명확히 안내한다.
- 과거 작업 중 checkpoint는 원문에 따라 row-preview 계약으로 보강할 수 있다. 모델 예산을 초기화하지 않고 저장된 raw prefix로 로컬 재개하는 경로를 검사했다.

## 회귀와 중간 발견

- 일반화된 합성 schema로 두 backend, 원본/집계 구분, bounded prefix, 재시작, 선택/원본 digest 보존, 한도·모호한 테이블·수동 거절·연결 없음·과거 모델 checkpoint·빈 응답·실제 페이지 표를 검사했다.
- 20,000행 파일 원본에 full-frame read를 실패시키고 전체 복원 한도를 1KiB로 제한해도 10행 prefix 표시가 성공했다. 이는 전체 데이터를 메모리에 다시 올리지 않는 경로 검사이며 대규모 성능 점수로 해석하지 않는다.
- 첫 확대 검사에서 3회귀 실패: 설명 전환이 계약 request key를 None으로 비우는 경로였다. None-safe 접근으로 수정했다. 첫 실DB 반복 검사도 두 backend에서 불필요한 재조회가 발생했다. LIMIT 결과의 `predicate_known=False`를 무조건 버리던 조건을 SQL 출처·무필터·raw 검증으로 보정하고 반복 SQL 0회를 다시 확인했다.
- 첫 최종 전체 검사: 690 PASS, 0 FAIL, 4 SKIP, 483 subtests, 98.60초. 이후 연결 부재 문구와 음수 행수 검사를 추가했고 최종 결과는 validation.json에 기록한다.
- 최종 전체 검사: **691 PASS, 0 FAIL, 4 SKIP, 483 subtests, 97.56초**. 행 미리보기 관련 8 PASS/4 subtests, compileall/diff-check/8504 health PASS. 최종 서버 PID21127에서 run `e270740853e1400f8fc5da5c02fef29f`도 표 표시·모델/SQL0회·기존 선택 보존을 확인했다.
