# 데이터 로딩·원본 보존·실행 위치 선택 계약

작성: 2026-09-24 · 상태: **계획 보강 / 구현·평가 미완료**

연결: [전체 요구사항](data_agent_requirements_and_evaluation_2026-09-24.md), [EDA](eda_exploration_contract_2026-09-24.md), [설계 리뷰](design_review_2026-09-24.md). 사용자 보고 사례를 요구사항으로 정리한 문서이며 해당 사례의 로그를 재현·확인한 진단 보고서는 아니다.

## 1. 해결할 문제와 불변 조건

사용자가 보고한 문제는 ① 잘못된 대용량 조회의 시간·비용 손실 ② 후속 질문 오해석으로 불필요한 재로딩 ③ EDA 조작으로 로딩 원본을 잃어 재조회 ④ SQL 집계와 원본 기반 탐색을 구별하지 못하는 것이다.

다음 조건을 실행 계층에서 강제한다.

1. **검증된 로딩 원본은 불변·보호 자산이다.** 필터·정렬·변환·집계·차트 생성·새 로딩 때문에 수정·교체·삭제하지 않는다.
2. **데이터 저장과 현재 선택은 별개다.** 새 결과를 저장하거나 화면에서 선택해도 기존 원본과 분석 분기는 남는다.
3. **현재 파생 결과가 부족하다고 바로 재조회하지 않는다.** 연결된 원본·다른 보유 데이터·저장 집계를 먼저 확인한다.
4. **새 Databricks 실행은 기존 승인 정책을 지킨다.** 차트 오류, 낮은 해석 확신, 캐시에서 사라짐 자체는 새 원격 조회의 근거가 아니다.
5. **새 로딩 실패는 기존 분석의 실패가 아니다.** 기존 데이터·선택·차트는 보존하고 실패한 후보만 격리한다.
6. **집계와 원본 중 하나를 항상 강제하지 않는다.** 목적·재사용 가능성·정확성·비용·보유 범위로 결정한다.

여기서 ‘원본’은 **사용자가 승인해 성공적으로 받은 행 수준 데이터 snapshot**이다. DB 전체를 받았다는 뜻이 아니다. 일부 기간/컬럼, 표본, 잘린 결과라면 그 범위를 명시한다. DB 집계 결과는 보존할 수 있지만 행 수준 원본으로 분류하지 않는다.

## 2. 데이터 역할과 탐색 상태

| 역할 | 내용 | 변경 규칙 |
|---|---|---|
| 보호 원본 | 검증된 immutable raw snapshot, 저장 manifest·digest·범위·source/version | 분석 도구에 수정/삭제 권한 없음. 메모리에 상주할 필요는 없음 |
| 파생 데이터 | 필터·컬럼 선택·정렬·파생 변수·cohort 등 | 새 ID와 parent/root ID·변환 명세로 생성; 원본 불변 |
| 통계 결과 | DB/로컬 집계, 지표·분모·grain·정확성 모드 | raw root와 구별하며 재집계 가능성 검증 |
| 차트 입력·이미지 | 집계/표본 참조, ChartSpec, 실제 파일 | 변경 시 버전 생성; 스타일 변경은 입력 재사용 |
| 로딩 후보 | 아직 검증/발행되지 않은 새 조회 결과 | 기존 ready 데이터와 선택을 대체하지 않음 |

화면 상태도 `선택한 source`, `탐색 기준 원본`, `현재 파생 데이터`, `현재 차트`, `승인 대기 로딩 후보`를 구분한다. 마지막으로 도구가 반환한 dataset을 무조건 다음 분석의 기준으로 삼지 않는다. “그중”은 현재 분기, “필터 전으로”는 부모, “이번에 로딩한 원본으로”는 해당 root를 참조한다. “전체”가 로딩된 범위인지 DB 전체인지 문맥으로 확정되지 않으면 짧게 확인한다.

여러 원본/후보가 같은 요청에 맞을 때는 현재 명시한 기준·source·snapshot·범위로 선택하고 근거를 남긴다. 선택이 결과 의미를 바꾸는데 근거가 없으면 사용자에게 선택지를 제시한다. 대화 간 자산 탐색은 권한 있는 workspace 경계 안에서만 수행한다.

## 3. 잘못된 대용량 로딩을 막는 단계

### 3.1 실행 전: 요청의 의미를 로딩 계획과 대조

LoadPlan은 기존 AnalysisPlan에 연결되는 계약이다. 요청/revision, 대상 catalog/schema/table, 필요한 컬럼, 기간·필터·timezone, raw/aggregate/sample 목적, grain/지표, 정확성·최신성, 예상 scan/반환 bytes와 unknown 여부, 시간/저장 한도, 승인 SQL 및 파라미터 fingerprint, 기존 데이터가 부족한 이유, 로딩 후 사용할 역할을 담는다.

먼저 보유 schema/외부 context와 요청을 근거로 SQL의 projection·predicate·join·aggregation을 대조한다. SQL 문법이 맞는 것만으로 합격하지 않는다. 중요한 source/기간/필터 변경은 현재 계획과의 차이를 보여준다. 잘못된 의미를 SQL과 계획에 똑같이 복제할 수 있으므로 사용자 원문·후속 변경·근거를 함께 추적하고, 의미가 결정되지 않은 조건은 임의로 채우지 않는다.

승인 카드에는 읽기 쉬운 대상·범위·필요 이유·예상 규모/미확인·기존 데이터 보존·후보의 용도를 표시하고 정확한 SQL을 확인할 수 있게 한다. **조회 승인과 기존 원본 삭제는 연결하지 않는다.** 승인 후 동일 계획을 다시 승인받게 하지 않으며, SQL/범위/연결이 바뀌면 새 승인을 요청한다.

EXPLAIN·schema refresh·COUNT·preview도 원격 실행이면 승인 대상이다. 모든 적재 전에 별도 COUNT나 preview를 강제해 조회 횟수를 늘리지 않는다. 보유 근거와 로컬 SQL 검증을 우선하며 추가 원격 검사가 필요한 이유·비용을 제시한다. 작은 LIMIT 결과의 성공은 전체 query scan 비용이나 전체 데이터 정확성의 증거가 아니다.

### 3.2 실행 중: 보호된 별도 후보로 적재

승인된 실행의 batch를 별도 staging에 기록한다. 첫 batch부터 schema·dtype·예상 grain 등 검사 가능한 조건을 점검하고 불일치·byte/시간/디스크 한도 초과 시 적절히 중단한다. 서버 실행 비용은 이미 발생할 수 있으므로 이를 실행 전 비용 검사의 대체로 삼지 않는다. source predicate는 계획/SQL 근거와 결과에서 확인 가능한 범위를 함께 검증하며 preview 몇 행으로 전체 범위를 증명하지 않는다.

이 단계에서 기존 root, active branch, 완료된 차트를 바꾸지 않는다. 잘린/중단된 후보는 complete로 표시하지 않는다. 이미 승인된 쿼리의 batch fetch와 새 SQL 실행을 구분한다. 제출 여부 불명의 쿼리는 자동 재제출하지 않는다.

### 3.3 실행 후: 검증·발행·선택을 분리

실제 schema·행수·byte·coverage·grain·source/version·digest와 LoadPlan을 대조한다. 기대와 다른 빈 결과/큰 결측 증가 등은 근거와 함께 점검하되 정상 빈 결과를 무조건 오류로 보거나 필터를 완화하지 않는다. 검증을 통과하면 새 immutable 자산으로 원자적으로 발행한다.

현재 revision의 명확한 요청이 새 데이터를 기준으로 쓰는 것이었다면 발행 후 선택 포인터를 변경한다. 저장된 기존 root는 유지한다. SQL 통계 조회 결과는 그 분석의 통계 자산으로 등록하며 기존 EDA root를 대체하지 않는다. 사용자가 이미 요청을 바꿨다면 늦은 결과는 해당 이전 요청에만 귀속한다. 실패 후보를 비우더라도 기존 자산은 건드리지 않는다.

## 4. 재사용 판단은 보유 자산 전체에서 수행

현재 `assess_reuse(info, need)`는 한 dataset과 요청을 비교한다. 그 결과 `query_source`를 받았다는 사실만으로 실제 재조회 필요성을 확정하면 안 된다. 상위 planner는 권한 있는 자산 registry와 parent/root 계보의 metadata를 검색한 후 최종 실행 위치를 결정해야 한다. 실제 payload 전체 로딩으로 후보를 탐색하지 않는다.

판정 결과는 `reuse`, `derive_local`, `scan_local`, `combine_local`, `request_remote_aggregate`, `request_remote_raw`, `clarify`, `blocked` 등의 의미로 구분한다. 이름은 기존 계약과 adapter로 맞춘다. 후보별 source·snapshot·컬럼·조건 포함관계·coverage·grain·지표 충분성·권한을 검증하고 실패 이유를 기록한다. 포함관계를 증명할 수 없다는 것과 실제 데이터가 없다는 것을 구분한다.

예: 현재 화면이 그룹별 건수여도 원본이 남아 있으면 원본에서 산점도를 만든다. 필터를 해제하면 좁은 파생본이 아니라 충분한 부모/root를 선택한다. 파일에 원본이 있으면 RAM cache miss를 원격 데이터 부재로 해석하지 않는다. 최신 데이터 요청 없이 로컬 snapshot으로 충분한 분석에 원격의 최신 여부 확인을 강제하지 않는다.

## 5. 로컬·원격·혼합 실행 선택표

| 상황 | 우선 선택 | 보존·정확성 조건 |
|---|---|---|
| 보유 raw로 조건 변경·변수 변환·여러 차트 가능 | 로컬 파생/집계, 큰 원본은 파일 선택 scan | 같은 root에서 분기, 신규 원격 0 |
| 보유 정확 집계로 같은 지표·차트 가능 | aggregate 재사용·재렌더링 | MetricSpec 충족; 중앙값/고유 건수 등 잘못된 재집계 금지 |
| 원격 대규모 데이터의 전체 건수·분포·기간별 지표 필요 | 승인형 DB filter/group/bin 집계 | 축약 결과만 수신; 기존 raw와 통계 자산 분리 |
| 원격 행 수준 자료로 반복 EDA가 목적 | 필요한 범위·컬럼의 raw를 승인 후 적재/보호 | 일회 집계보다 재사용 가치 평가, 무조건 전체 테이블 다운로드 금지 |
| 보유 범위 밖 기간·컬럼 필요 | 부족한 부분 적재 또는 새 snapshot 계획 비교 | 부분 결합의 key·중복·범위·version 일관성을 증명할 때만 합침 |
| 전체 통계와 세부 EDA가 모두 필요 | DB 정확 집계 + 필요한 raw/명시된 sample의 혼합 | 각각 scope/version/정확성 표시, sample을 전체 근거로 오인 금지 |
| 로컬 정확 계산이 예산 초과 | 파일 실행/다른 계획 평가, 필요 시 원격 집계 승인 제안 | 원본 삭제 금지, 몰래 sample/근사 전환 금지 |
| 최신 원본 요청 | 새 version 조회 승인 | 이전 snapshot 보존, 새 결과 검증 후 해당 요청에 연결 |

추가 컬럼을 가져와 기존 행에 붙이는 작업은 안정적인 유일 key·동일 snapshot이 확인되어야 한다. 기간 확장도 중첩·누락·원본 수정 여부를 검증한다. 증분 적재가 안전하지 않으면 새 snapshot을 별도로 만들며 기존 데이터를 덮어쓰지 않는다.

비용 판단은 query scan·전송·적재·저장·로컬 실행·후속 EDA에서의 재사용을 함께 고려한다. **이미 적재한 비용은 다시 지불할 비용으로 계산하지 않는다.** 앞으로 필요한 전송/계산과 재사용 가능성을 비교하고, 예상값·관찰값·unknown을 분리한다. 반복 탐색 가능성은 사용자 목적과 세션 이력에 근거하며 임의 미래 사용량을 확정하지 않는다.

## 6. 원본의 물리적 보존과 용량 정책

보호는 DataFrame을 매번 deep copy하거나 RAM에 영구 보관한다는 의미가 아니다. 원본의 영속 snapshot·manifest·checksum은 유지하고 RAM cache는 해제할 수 있다. 파생 작업은 읽기 전용 원본 참조, 실행 시점의 부분 읽기, bounded 작업 버퍼를 사용한다. 변환 명세만 저장해도 되는 경우에는 논리적 파생 view로 관리한다. 코드 실행 worker도 원본 저장 위치에 쓰기/삭제할 수 없어야 한다.

활성 EDA root와 참조된 보호 snapshot은 자동 cache 정리·quota 회수·기본 TTL로 삭제하지 않는다. 새 적재 공간이 부족하면 staging·재생성 가능한 cache부터 정책 범위에서 정리하고, 여전히 부족하면 **새 적재를 멈추거나 범위/저장소 변경을 제안**한다. 기존 원본 삭제로 새 로딩 공간을 몰래 확보하지 않는다.

이 정책은 무한 보존 약속이 아니다. 사용자 명시 삭제/보호 해제나 사전에 명시한 조직 보존 의무는 별도 수명 정책으로 처리한다. 만료가 예정되면 영향받는 분석·차트와 재계산 가능성을 알리고 현재 원본이 보호되어 있는지 화면에 표시한다. 삭제·권한 회수 후 접근 제한은 보존 정책보다 우선하며 데이터가 없을 때는 자동 재조회하지 않는다. 저장장치 자체 손상/유실에 대한 보장은 배포의 백업·복구 정책과 별도로 검증해야 한다.

원본 존재만으로 충분하지 않다. filter/derive/join/차트/새 로딩/실패/재시작 후 원본 ID·schema·행수·digest·readability가 그대로인지 시험한다. 전체 checksum 재계산은 매 요청마다 하지 않고 저장/무결성 검증 계층과 회귀 시험에서 관리한다.

|---|---|---|
| J21 | raw 적재 → 필터 → 컬럼 변환 → 집계 → 차트 여러 개 → 원본 복귀 → 재시작 | 원본 ID/digest/행수·읽기 가능 유지; 파생 lineage 연결; 최초 적재 이후 원격 0 |
| J22 | 차트 수정/모호한 후속 질문을 재로딩으로 오해한 계획, 잘못된 source·기간·컬럼 SQL | 의미 불일치/불명확성을 실행 전에 차단 또는 확인; 기존 원본/선택 유지; 승인 없는 실행 0 |
| J23 | 새 후보 로딩 중 schema 불일치·중단·디스크 부족·빈 결과·새 요청 도착 | 기존 자산 보존; 불완전 후보 ready 금지; 검증/현재 revision 조건 전 active root 변경 0; 정상 빈 결과는 정상 처리 |
| J24 | SQL 전체 집계 ↔ 보유 raw EDA ↔ 부족한 범위 추가 ↔ sample 비교 | 올바른 실행 위치·계보·coverage; aggregate가 raw를 덮어쓰지 않음; 증분 결합 증명 없으면 차단; 새 원격 SQL마다 승인 |

평가에는 “이 차트만 바꿔줘”, “원래 데이터로 돌아가”, “그중”, “전체로”, “최신 것으로”의 한국어 변형과 미지 schema를 넣는다. 의도/원격 필요 여부의 정답은 실행 전에 fixture로 고정한다. J22에는 사용자가 실제로 새 데이터를 요청한 정상 사례도 넣어 필요한 로딩을 무조건 막는 설계를 방지한다.

지표: 불필요한 원격 실행 수, 잘못된 적재 계획의 실행 전 차단률, 오해석으로 생긴 승인 요청 수, 원본 훼손/참조 소실 수, 재시작 뒤 로컬 복구율, 재사용률, 반복 EDA 누적 지연·전송 bytes·재계산량. 승인 준수와 의도 정확성을 따로 채점한다. 사용자가 승인했다고 잘못 해석한 계획을 정답으로 판정하지 않는다. 성공률 수치는 아직 측정하지 않았다.

## 8. 기존 구현 계획에 반영할 우선순위

| 기존 Task | 추가 완료 조건 |
|---|---|
| T01~T02 | 사용자 보고 손실 사례 J21~J24의 fixture/oracle·원본 불변·로딩 필요성 평가 먼저 고정 |
| T05 | 분석 의도와 load intent 분리, root/branch/candidate 역할, 모호한 범위 확인 |
| T06 | registry/계보 전체 reuse 판정, LoadPlan·승인 차이 표시, 기존 원본 보존을 P0로 강제 |
| T07 | 보호 snapshot·후보 staging·atomic 발행·quota admission·재시작 복구를 P0로 우선; 대용량 최적화는 후속 |
| T08 | 로컬/raw/remote aggregate/hybrid 후보의 의미·미래 비용 비교, 증분 결합 조건 |
| T09~T10 | 모든 조작·시각화의 원본 불변, 파생 계보, root 복귀 및 SQL 통계 결과 분리 |
| T11~T13 | 실제 모델의 오해석·실패 주입·반복 EDA·화면/재시작 전 여정, 손실/불필요 재조회 gate |

DB 조회 최적화보다 먼저 보존 경계와 로딩 필요성 판단을 검증한다. 기존 dataset ID·승인 ledger·checkpoint는 유지하고 역할/보호 metadata를 추가하는 migration을 설계한다. 기존 자산의 root·coverage·version을 모르면 추정하지 않고 unknown 상태로 보존한다. 이번 문서로 런타임의 원본 불변성이 이미 보장됐다고 주장하지 않는다.
