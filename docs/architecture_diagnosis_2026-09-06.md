# Telly 구조 진단 — 2026-09-06

이 문서는 기존 SQL/EDA 분리 구조를 진단한 당시 기록이다. 이후 pages/Telly.py가 AnalysisSession 기반으로 변경되어 아래 페이지 경로·행 번호는 현재 코드와 다를 수 있다. 최신 구현 기준선과 전환 순서는 [LangChain/LangGraph 전환 설계](langchain_migration_design_2026-09-06.md)를 따른다.

## 범위와 결론
현재 코드, 저장된 TableContext 메타데이터, WORK_HISTORY.md, 프로젝트 로그, 테스트 구현을 검토했다. 외부 LLM/Databricks 및 실제 UI 재현은 수행하지 않았다. 직전 점검의 정적 테스트 통과 결과를 참고하되 자연어 이해 검증과 구분했다.

현재 구조는 질문 전체를 이해하고 검증된 답을 만드는 분석 실행기보다, 시각화 전용 계획기와 SQL/EDA 에이전트의 병렬적인 처리 경로에 가깝다. 여기서 병렬은 동시 실행이 아니라 별도 경로가 공존한다는 의미다. 기능별 보완은 축적되어 있지만 분석 의도, 대화 상태, 실행 결과의 공통 계약이 부족하다.

## 주요 근거

1. **자연어 조건의 일부만 LLM이 담당한다.** `utils/chatbot_plan.py:134`의 LLMVisualizationPlan에는 filters가 없다. `build_llm_visualization_plan()`은 차트/축을 LLM으로 정하고, 마지막에 filters/filter_conditions/rank를 deterministic fallback에서 가져온다. 모델이 문장을 이해해도 실행 조건은 정규식이 해석한 범위로 제한된다. 조건 coverage 역시 특정 범위/보유 표현 중심이므로 모든 조건을 검증하지 못한다.
2. **실행 경로마다 판단 기준이 다르다.** `core/chat_flow.py:1089`부터 명령, 키워드 강제 SQL, controlled flow, LLM router, SQL→EDA rerun이 연결된다. controlled 경로는 DataRequirement/DataFrameState를 검증하지만 legacy router는 현재 행 수 10 이하를 preview로 간주한다(`core/chat_flow.py:1246`). 정당한 소규모 집계 결과와 샘플을 구분하지 못하고, 11행 이상 데이터가 질문에 충분한지도 router에 전달하지 않는다.
3. **대화 맥락이 분산되어 있다.** planner와 router에는 현재 질문만 전달된다. `pages/Telly.py:78` 부근에서 SQL/EDA history가 분리되고 데이터 변경 시 EDA history가 초기화된다. controlled 결과는 대화 표시 로그에 기록되지만 다음 planner 입력에 과거 계획/결과가 포함되지 않는다. 따라서 '그중', '같은 조건', '아까 결과와 비교'의 해석을 일관되게 보장하기 어렵다.
4. **테이블 프로파일이 업무 의미를 충분히 담지 못한다.** `utils/table_context.py:25`의 컨텍스트는 타입/통계/alias 중심이다. 자동 alias 생성은 컬럼명 표기 변환이며, 업무 개념의 정의나 단위·분모·조인 관계를 체계적으로 표현하지 않는다. 저장된 bank_loan 기본 프로파일은 18개 컬럼 모두 alias가 없었다. override가 있는 테이블도 있으므로 이 수치를 모든 런타임 컨텍스트의 상태로 일반화하지 않는다. '%table training'은 이 코드에서 메타데이터 프로파일링이며 모델 학습 자체가 아니다.
5. **분석 답변의 완료 조건이 약하다.** `core/chat_flow.py:571` 부근의 controlled 결과는 차트 생성과 기술 요약 문구로 끝난다. 질문에 대한 수치적 결론, 근거 표, 적용 조건, 데이터 범위의 공통 결과 모델이 없다. figure가 없어도 명시적인 실패 분기 없이 success를 기록할 수 있다. legacy 경로는 모델의 자유 텍스트와 도구 실행 결과를 출력한다. 플롯 생성과 사용자가 원한 정보 전달은 다른 검증 대상이다.
6. **모델에 형식·도구·코드 부담이 집중된다.** `core/agent.py:54`는 JSON structured-chat agent를 사용하며 parsing error 재시도가 있다. `core/prompt.py:58`에는 도메인별 절차, 시각화 정책, 실행 코드와 엄격한 JSON 규칙이 함께 들어간다. JSON 외 출력 금지와 코드 블록/Observation 예시가 공존하고, Thought에서 점검하라는 표현과 Thought 출력 금지도 섞여 있다. 구조적 부담은 확인했지만 현재 사용 모델의 개별 실패율은 측정하지 않았다.
7. **검증이 사용자 목표보다 내부 실행에 치우친다.** `test_scenario.py:4179`의 CSV E2E는 sql/eda agent와 llm을 None으로 전달하고 SQL을 CSV shim으로 교체한다. 이는 결정적 실행 경로 회귀 검증에 유용하지만 실제 모델 이해력/도구 사용/Databricks 통합 검증이 아니다. 외부 LLM 테스트는 router 중심이며 registry LIVE-001은 비활성이다.
8. **UI와 실행 상태의 결합이 크다.** core/chat_flow.py 1,506행에서 Streamlit UI, 전역 session state, 계획, 실행, 에러 처리, 로그, rerun을 함께 다룬다. WORK_HISTORY에 last_agent_mode 변경 및 rerun 키워드 재적용으로 체이닝이 끊겼던 이력이 있다. 과거 버그는 수정된 것으로 기록되어 있으나 같은 결합 구조의 유지비는 남아 있다.

## 오프라인 재현
실제 데이터/외부 서비스 없이 numeric 컬럼 metric_a, metric_b를 가진 trained 테스트용 TableContext로 build_controlled_plan 및 validate_condition_coverage를 호출했다.

- 정상 대조군: `metric_a가 10 이상인 metric_b 분포를 그려줘` → `WHERE metric_a >= 10`.
- 누락 사례: `metric_a가 10 미만이거나 20 초과인 metric_b 분포를 그려줘` → `WHERE metric_a < 10`.
- 두 요청 모두 coverage `ok=True`. 두 번째는 의도한 OR 조건 중 `metric_a > 20`이 누락됐다.
- 현재 LLM 경로도 필터를 deterministic fallback에서 가져오므로 동일 취약점이 연결된다. 단, 실제 LLM 호출로 해당 문장의 전체 턴을 재현한 것은 아니다.

## 권장 방향과 순서

목표 흐름: 질문 + 공유 분석 상태 → 분석 계획 → 데이터/조건 검증 → SQL 또는 Python 실행 → 결과 검증 → 근거를 포함한 답변.

1. 현재 실패 질문을 실제 표현 그대로 고정하고, 정답 데이터 범위/수치/조건을 가진 평가 세트를 만든다. OR, NOT, 기간, 동일 뜻의 표현 변경, 후속 질문, 테이블 전환을 포함한다. 내부 스키마와 차트 유형 검사 외에 결과 수치 정확성을 검사한다.
2. 시각화 계획을 AnalysisRequest로 확장한다. 데이터 출처, metric, filters(AND/OR/NOT 식 트리), 그룹, 기간, 비교 기준, 출력 형태를 명시한다. LLM이 의미를 제안하고 코드는 실제 스키마·타입·집계 타당성·실행 한도를 검증한다.
3. 하나의 분석 세션 상태를 두고 이전 요청, 확정한 조건, 데이터 출처, 결과 artifact를 보존한다. 되묻기에 대한 답변도 이 상태에 병합한다.
4. 공통 AnalysisResult에 근거 수치/표/차트/적용 조건/데이터 범위/제약을 담고, 이를 바탕으로 답변한다. 실행 완료와 분석 정확성을 분리한다.
5. 실행기를 Streamlit 밖에서 호출 가능하게 분리하고, 하나의 검증된 경로부터 새 구조로 옮긴다. 기존 TableContext, readiness gate, SQL 로더, 렌더러, trace와 회귀 테스트는 재사용한다.

전면 재작성이나 에이전트 수 증가를 먼저 하기보다, 단일 테이블의 조건 조회·집계·비교를 공통 계약으로 끝까지 검증하는 것이 우선이다. 모델 변경의 효과는 이 구조와 평가를 갖춘 뒤 분리 측정한다.

## 추가 진단: 에이전트 구조와 요청 간 연결

### 판단
SQL/EDA 내부에는 AgentExecutor의 도구 선택→관찰→다음 행동 반복이 존재하므로 에이전트 요소가 없다는 진단은 부정확하다. 다만 전체 애플리케이션은 사용자 목표를 여러 턴에 걸쳐 유지하는 분석 에이전트보다, 개별 요청을 처리하는 워크플로에 국소적인 에이전트를 붙인 구조에 가깝다. 이전 진단은 필터/실행 계약에 집중했으며, 이것만 개선해서는 대화 연속성 문제가 해결되지 않는다.

### 대화 데이터의 실제 흐름
- `ui/chat_log.py:21`: conversation_log는 화면 표시, figure 연결, 평가 등에 사용된다. 현재 planner/router의 입력으로 전달되지 않는다.
- `pages/Telly.py:64`: SQL과 EDA는 별도의 lc_msgs:sql / lc_msgs:eda 기록을 갖는다. 같은 경로 안에는 대화 기억이 있으므로 '모든 대화 기록이 없다'는 표현은 맞지 않는다.
- `pages/Telly.py:66`: 데이터 변경 시 EDA 기록을 삭제한다. `ui/data_state.py:22`는 데이터 signature로 변경을 판정하므로 분석 중 데이터 갱신도 이 조건에 걸릴 수 있다.
- `ui/history.py:4`: 기록은 최근 24개 메시지로 잘리며, 확정한 조건/목표를 구조화해 유지하는 별도 요약은 이 경로에 없다.
- `utils/chatbot_plan.py:1422`: 시각화 planner는 현재 질문, 테이블, 컬럼 metadata로 호출된다. 이전 목표, 대화, 이전 계획, 이전 결과가 입력에 없다.
- `core/llm_router.py:16`: router는 현재 질문과 preview 여부만 받는다. 이전 요청이 어느 작업인지 이해하기 전에 SQL/EDA를 선택한다.

### 되묻기의 단절
`core/chat_flow.py:402`에서 clarification_question을 표시하고 로그에 저장한 다음 return True한다. pending clarification의 원래 요청, 미확정 필드, 후보, 다음 답변 병합 규칙은 이 경로에 없다. 따라서 질문 출력 기능은 있으나 사용자가 짧게 답했을 때 원래 분석을 재개하는 프로토콜은 없다. 예를 들어 '어떤 컬럼을 볼까요?'에 '온도'라고 답해도, planner에는 '온도'라는 새 입력과 테이블 metadata만 전달된다. 실제 모델 결과는 측정하지 않았지만 이전 요청의 의도를 전달하지 않는 호출 구조는 코드로 확인했다.

### 목표 추적과 후속 요청의 해석
현재 DataFrameState에는 출처/SQL/컬럼/행 수 등 데이터 상태가 있다. 반면 '현재 분석 목적', '합의된 모집단과 기간', '이번 발화가 조건 수정인지 추가 분석인지', '가리키는 이전 결과', '미해결 질문', '완료 기준'을 공통으로 저장하고 planner에 전달하는 상태 모델은 찾지 못했다.

예상 대화: '지난달 오류 많은 장비를 찾아줘' → '그중 A 모델만' → '이전 달과 비교해줘'. 이를 수행하려면 최초 작업의 장비 범위, 오류 지표, 지난달 기준을 유지한 채 모델 조건을 추가하고 비교 기간만 확장해야 한다. 현재는 발화마다 routing/planning을 다시 하므로 해당 참조를 일관되게 해석할 기반이 약하다. 이 예시는 구조 설명용이며 live 재현 결과가 아니다.

### 작업 연결과 에이전트의 판단 구분
`core/chat_flow.py:1428`의 SQL→EDA 연결은 SQL 성공과 chaining flag에 따라 원문을 auto_eda_pending에 넣고 UI를 rerun하는 방식이다. EDA에는 원래 질문과 현재 컬럼/행 수 및 이미 필터링되었다는 안내가 추가된다. 이는 작업 순서 자동화다. 분석 결과를 관찰해 '사용자 목표가 충족됐는지, 다른 비교나 추가 조회가 필요한지' 판단하는 공통 상위 루프는 확인되지 않았다. SQL/EDA 내부의 도구 반복과 파싱 오류 재시도는 존재하므로 이를 전체적으로 '실행 반복이 없다'고 표현해서는 안 된다.

### 수정된 설계 우선순위
1. SQL/EDA 선택 전에 사용자 발화를 해석하는 대화 계층을 둔다. 새 목표, 조건 추가/수정, 이전 결과 참조, 되묻기 답변을 최근 대화와 명시적인 분석 상태에 근거해 구분한다.
2. 목표, 확정 조건, 미확정 항목, 현재 결과 참조를 공유 상태로 저장한다. 새 데이터 로딩은 분석 목표/합의를 자동 삭제하지 않는다. 명시적 주제 전환과 테이블 전환은 참조 유효성을 다시 검증한다.
3. 상위 분석 에이전트가 데이터 탐색/SQL/분석/차트 기능을 도구로 사용하고, 관찰한 결과를 바탕으로 다음 행동을 결정하도록 한다. 각 기능을 별도 대화 주체로 유지할 필요는 없다. 내부 전문 실행기를 남겨도 목표와 결과를 명시적으로 공유한다.
4. 계획은 실행을 위한 도구다. 사용자의 모든 자연어를 고정된 차트 스키마에 먼저 맞추지 않는다. 이해·탐색·질문·실행·답변을 선택할 수 있게 하고, 실행 시에는 검증된 입력과 예산/횟수 한도를 둔다.
5. 단일 프롬프트 테스트에 더해 3~5턴 대화 평가를 우선 만든다. 조건 유지, 지시어 해소, 수정 의도, 되묻기 재개, 이전 결과 비교 및 주제 전환을 검증한다.

이 진단은 코드 경로 확인에 근거한다. 실제 사용 모델의 문장 이해 능력과 입력 컨텍스트 부족의 기여도는 live 대화 평가로 분리해야 한다. 전체 히스토리를 무제한 추가하거나 모델만 교체하는 것으로 공유 상태/참조/목표 검증을 대체할 수는 없다.
