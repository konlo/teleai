# Agent 개발·검증·출시 기준

작성일: 2026-09-07. 사용자와 논의한 개발 기준을 보존한 문서다. 이 문서의 존재는 아래 검증의 완료나 출시 승인을 뜻하지 않는다.

## 목적

모델의 작은 도구 선택 오류가 사용자 작업 전체를 중단시키지 않도록 한다. 테스트 개수나 자연스러운 답변만으로 출시 가능성을 판단하지 않는다. 시간이 부족하면 검증된 지원 범위를 좁히고, 검증되지 않은 기능을 가능하다고 안내하지 않는다.

## 모든 과제에서 확인할 사항

1. 사용자 여정: 자료 탐색 → 컬럼 확인 → 로딩 승인 → 분석 → 후속 질문 → 차트 수정까지 연결해서 검증한다. 로딩 전 탐색을 포함한다.
2. 도구 계약: 잘못된 도구·ID·인자를 실행 전에 검증한다. 복구 가능한 오류는 수정 방법과 함께 도구 관찰로 반환한다. 예상하지 못한 오류를 성공으로 숨기지 않는다.
3. 상태 구분: 테이블 설명, 로딩된 원본, 집계 결과, 선택한 차트, 승인 대기를 분리한다. 참조의 존재와 데이터 범위를 실행 전에 확인한다.
4. 복구: 기존 데이터와 요청을 보존한다. 복구 가능한 오류만 제한된 횟수로 수정하며, 반복 실패에는 원인과 다음 행동을 안내한다. 제출 여부가 불명확한 원격 조회는 자동 재실행하지 않는다.
5. 정확성: 조건·기간·분모·범위·집계 수준을 실제 도구 결과와 비교한다. 수치와 이미지를 생성하지 않고 생성했다고 답하지 않는다.
6. 관측: 실행 ID로 도구 실행과 실패 단계·예외 위치를 추적한다. 비밀정보와 데이터 원문을 진단 로그에 무분별하게 기록하지 않는다.
7. 회귀: 도구·프롬프트·상태 변경 시 관련 정상·실패·후속 대화 시나리오를 자동 재실행한다. 데이터별 지식은 외부 fixture/context로 관리한다.
8. 스키마 중립성: agent 코드와 공통 prompt에 특정 테이블명·컬럼명·업무값을 넣지 않는다. 필요한 컬럼 의미는 실행 시점의 로딩 dataset metadata 또는 TableContext에서 확인한다. 정보가 없거나 stale이면 추측하지 않고 schema inspection 또는 승인형 discovery 계획에서 멈춘다.

## 자동 평가 두 층

- 빠른 계약 테스트: 승인 우회, 잘못된 ID, 없는 컬럼, 중복 제출, 재시작과 복구를 매 관련 변경마다 검사한다.
- 실제 모델 종단 평가: 대표 사용자 여정을 자연어와 후속 질문으로 실행한다. 최종 수치, 데이터 범위, 조회 횟수, 승인 준수, 차트 생성, 소요 시간을 확인한다. 반복 실행 결과와 실패도 기록한다. 대역 모델의 통과를 자연어 품질 검증으로 계산하지 않는다.

수동 질문을 하나씩 추가하는 방식에만 의존하지 않는다. 대표 여정과 정답/불변 조건을 고정된 평가 묶음으로 관리한다. 성공률과 지연시간의 수치 기준은 실제 측정 및 제품 요구에 맞게 확정하며 아직 정하지 않은 기준을 충족했다고 선언하지 않는다.

## 출시 차단 조건

- 승인 없는 데이터 조회 또는 재로딩.
- 잘못된 조건·기간·모집단으로 계산하거나 데이터를 유실함.
- EDA 변환·새 로딩·quota 정리 때문에 보호 원본이 수정/삭제되거나 원본 복귀에 불필요한 원격 조회가 필요함. [보존 계약](data_loading_and_preservation_contract_2026-09-24.md)의 J21~J24로 검증.
- 새 로딩 후보가 검증·발행되기 전에 기존 분석 기준을 대체하거나, 집계 결과를 raw 원본으로 취급함.
- 일반적인 지원 범위 질문에서 복구 가능한 도구 오류가 대화를 중단시킴.
- 실제 운영 연결 또는 핵심 사용자 여정이 검증되지 않음.

출시 범위와 환경을 명시한다. 지원 범위 밖 요청에는 제한 이유와 가능한 대안을 안내한다. 미검증 기능을 전체 기능 성공으로 합산하지 않는다.

## 작업 완료 정의

코드 변경뿐 아니라 사용자 여정, 실패 복구, 관련 회귀 검사, 진단 기록을 확인해야 한다. 결과 보고에는 실행한 검증, 실제 증거, 수행하지 못한 검사와 남은 제한을 구분한다.

## 작성 시점의 상태

- bank_loan 실패 원인과 수정: [진단 기록](bank_loan_failure_2026-09-07.md).
- 현재 작업과 검증: [작업 현황](agent_validation_tasks.md), [검증 보고서](t07_t08_validation.md).

## 평가 실패의 개선 절차

실패가 발생하면 특정 질문/테이블만 통과시키는 예외 대신, 부족했던 공통 agent 기능을 보강한다.

1. 최초 실패의 요청, 결과, 실행 ID와 모델/도구 관찰을 보존하고 독립적인 기대 결과를 정한다.
2. 모델 추론·의도/범위 결합·계획·도구 계약·데이터 계보·완료 검증·환경 장애 중 원인을 구분한다.
3. 이미 검증된 결과와 원본을 보존하고, 남은 목표에 대해 근거가 있는 대체 도구/계획만 실행한다. 재시도·시간·도구 예산과 정확한 원격 SQL 승인은 유지한다.
4. 복구가 불가능하면 미완료 목표와 원인을 사실대로 남긴다. 사용자의 조건을 줄이거나 새 데이터를 임의로 받아 성공으로 바꾸지 않는다.
5. 실패 재현, 정상 여정, 잘못된 범위/승인/중복 실행 차단, 중간 결과·재시작 보존을 함께 검증한다.
6. 최초 실패와 수정 후 결과를 분리해서 보고한다. 장애 주입·대역 모델·실제 모델·실제 원격 데이터 검증을 혼합한 성공률로 표시하지 않는다.

## 2026-09-27 개발·검증 SQL 권한 갱신

사용자가 이번 agent 보강/검증의 SQL을 추가 확인 없이 사용할 수 있다고 명시했다. 이 작업에서는 필요한 읽기 전용 SQL을 자율 실행하고 정확한 실행 내역을 남긴다. 이 승인을 매 query 재질문으로 바꾸지 않는다. 제품의 일반 사용자 승인 기본값, 중복 실행/불명확한 제출 상태 방지, 원본 보존은 유지한다.
