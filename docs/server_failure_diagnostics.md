# 서버 실패 진단 안내

서버에 외부 접속할 수 없고 로그 파일도 반출할 수 없는 운영자를 위한 안내다. 전체 로그 대신 화면의 짧은 진단 요약에서 공유 가능한 코드·상태만 전달한다. 이 정보로 실패 단계를 좁힐 수 있지만, SQL 의미나 통계 정답까지 자동으로 판정할 수는 없다.

## 화면에서 확인하는 순서

1. 문제가 발생한 **같은 대화**를 유지한다. 이상한 답변도 실패로 취급한다. 예외창이 없어도 진단할 수 있다.
2. 채팅 입력창 위 **문제 진단 · 로그 원문 없이 확인**을 펼친다.
3. 화면에 오류 ID가 있으면 입력한다. 없으면 ID를 비워 두고 **진단 요약 확인**을 누른다. 최근 실행을 조회한다. 다른 요청을 보내기 전에 실행 ID를 기록하면 혼동을 줄일 수 있다.
4. 12줄 요약에서 허용되는 항목만 옮겨 적는다. 아래 JSON은 상세 확인용이며 파일을 보내지 않아도 된다.
5. 새 대화로 바꾸었거나 로그가 순환 삭제되면 `기록 없음`이 나올 수 있다. 이를 정상 판정으로 해석하지 않는다.

이 버튼은 보관된 로그만 읽는다. 모델, SQL, 재시도, 데이터 로딩을 실행하지 않는다.

## 알려줄 내용

다음 틀을 채우면 된다. ID 자체도 반출 제한 대상이면 생략하고, 내부에서는 같은 ID인지 확인한다. 요청·답변은 원문을 보낼 필요 없이 테이블 A, 컬럼 X처럼 익명화해서 설명한다.

```text
증상: 예) 테이블 목록 요청에 실제 목록 없이 나중에 알려준다고 답함
기대/실제: 예) 목록 표시 / 미래 안내 문장만 표시
처음부터 발생 또는 직전 작업: 예) schema 선택 후 후속 질문에서 발생
시각(UTC):
버전 / 경로:
실행 ID / 오류 ID: (공유 가능할 때만)
상태 / 진단 코드:
주 모델 호출 / 로컬 도구 / 원격 도구 시작:
조회 장부 상태 / 저장 결과 재사용:
완료 판정 이유 / 미충족 항목:
오류 단계 / 유형 / HTTP / 파일·줄·함수:
복구 재계획 횟수 / 로그 완전성:
```

운영자가 특히 확인할 항목은 다음과 같다.

| 확인 항목 | 판단에 쓰는 근거 |
| --- | --- |
| `runtime.route`, `revision_at_first_runtime`, `packages` | 실행 계열과 의존성 차이. `langgraph-v1`인지 확인 |
| `status`, `completion.reason`, `missing_capabilities` | 실행은 끝났지만 agent가 목표를 완료하지 못했는지 확인 |
| `model_calls`, `proposed_tool_calls`, `local_tools_started` | 주 분석 모델이 도구를 제안했는지, 로컬 실행이 관측됐는지 비교 |
| `remote.started`, `states`, `cached_receipts` | 원격 도구 진입·완료·불명확한 제출·저장 결과 재사용 구분 |
| `errors[].stage`, `error_type`, `http_status`, `frames` | 모델 호출, SQL, 로컬 도구, 이미지 표시 중 실패 위치 식별 |
| `recovery_replans`, `deferred_reply_blocks` | agent가 재계획했는지, 근거 없는 미래 안내를 차단했는지 확인 |
| `last_tool_events` | 마지막 6개 도구 시작·결과·거절 상태와 오류 코드 |

`model_calls`는 계측된 주 분석 모델 호출 수다. 모든 의미 해석/요약의 과금 호출 수가 아니다. `remote.started`는 원격 **도구 진입 수**이며 실제 DB 제출 횟수가 아니다. 저장 결과 재사용이나 실행 전 검증 실패도 포함될 수 있다. 미래 안내 차단 횟수는 여러 검증 계층의 관측 합계이며 고유 답변 수가 아니다.

## 코드별 확인 방법

| 진단 코드 또는 상태 | 의미와 확인할 내용 |
| --- | --- |
| `DEFERRED_REPLY_BLOCKED` | 근거 없는 “결과가 도착하면 알려주겠다” 문장을 차단했다. `status=answered`면 이후 복구됐을 수 있다. 계속 그 문장이 보이면 같은 실행인지, 최신 화면/버전인지 함께 확인한다. |
| `NO_TOOL_EXECUTION_OBSERVED` | 이 실행에서 계측된 도구 실행이 없다. 설명 요청이나 저장 결과 재사용은 정상일 수 있다. 실제 조회가 필요한 요청이었는지 알려준다. |
| `AGENT_NOT_COMPLETED` | agent가 완료 판정을 받지 못했다. `completion.reason`, `missing_capabilities`, 복구 횟수를 확인한다. |
| `remote.states.completed` | 조회 장부에 완료 기록이 있다. SQL 완료와 분석/시각화 완료는 다르다. 이후 도구·완료 판정·이미지 표시를 확인한다. |
| `remote.states.failed` | 실행기가 제출 전 실패로 분류했다. `query_databricks` 오류의 HTTP와 유형을 확인한다. |
| `REMOTE_SUBMISSION_UNCERTAIN` | 제출됐는지 확정하지 못한다. 동일 요청을 반복 실행하지 말고 서버 내부 Databricks 실행 이력과 대조한다. 확인 결과만 전달한다. |
| `CHART_DISPLAY_FAILED` | 차트 생성 뒤 파일/표시 검증 단계에서 실패했다. 과거 차트를 다시 표시하다 발생할 수도 있으므로 최근 SQL 실패라고 단정하지 않는다. 해당 오류 ID와 파일·줄을 확인한다. |
| `NO_TERMINAL_EVENT` | 종료 이벤트가 없다. 아직 실행 중인지, 프로세스가 종료됐는지, 로그가 유실됐는지 이 코드만으로 구분할 수 없다. 내부 서비스 관리자에서 재시작/OOM/디스크 부족 여부를 확인한다. |
| `RUN_START_NOT_RETAINED` | 시작 이벤트가 보관 범위 밖이거나 실행 외부 UI 오류다. 버전/횟수 정보가 불완전할 수 있다. |
| `ERROR_OBSERVED` | 중간 예외가 관측됐다. 최종 성공했으면 복구된 예외일 수 있으므로 이 코드만으로 최종 실패라고 판단하지 않는다. |
| `found=false` | 해당 대화의 보관 로그에서 찾지 못했다. ID·대화·로그 위치·보관 기간을 확인한다. |

HTTP 401/403은 **실패 단계와 함께** 알려준다. 모델 인증과 DB 권한은 별개다. HTTP 400만으로 프롬프트 잘못, 서비스 장애, 사용량 제한을 확정할 수 없다. `model_provider_temporarily_unavailable`이라는 과거 분류명도 단기 장애의 증거는 아니다.

## 화면을 사용할 수 없을 때

화면에 표시되는 서버 내부 `runtime.jsonl` 경로를 사용한다. 서비스와 동일한 Python 환경에서 실행한다. 아래 경로와 ID는 실제 값으로 바꾼다.

```sh
python scripts/diagnose_agent_run.py --log /실제/대화/경로/runtime.jsonl --error-id 오류ID --brief
python scripts/diagnose_agent_run.py --log /실제/대화/경로/runtime.jsonl --run-id 실행ID --brief
python scripts/diagnose_agent_run.py --log /실제/대화/경로/runtime.jsonl --brief
```

ID가 없으면 마지막 명령이 최근 실행을 조회한다. `--brief`를 빼면 같은 허용 항목의 JSON이 출력된다. 찾으면 종료 코드 0, 못 찾으면 1이다. **0은 분석 성공 판정이 아니다.**

기본 로그 위치는 프로젝트의 `.telly_runtime/v1/<대화 scope hash>/runtime.jsonl`이다. `TELLY_V1_STORAGE`를 지정했다면 그 경로 아래에 있다. scope hash는 대화 URL의 ID와 다르므로 같은 값의 폴더를 찾으면 안 된다. 위치만 찾을 때는 저장소 루트에서 다음처럼 검색한다.

```sh
find /실제/저장소/루트 -name runtime.jsonl
```

프로세스가 시작조차 못 하면 runtime 로그도 없을 수 있다. 이때는 서버 내부 서비스 로그에서 마지막 예외의 **클래스, 모듈/파일, 줄 번호**만 확인한다. 배포 점검은 다음으로 수행한다.

```sh
python scripts/diagnose_checkout.py
```

## 적용과 보관 범위

- 새 계측은 LangChain v1의 `ui/analysis_page.py` 경로에 적용된다. 구버전 `ui/legacy_telly.py`에는 이 진단 UI가 없다. 메뉴가 없으면 먼저 실제 branch/revision과 서비스 Python의 LangChain 버전을 확인한다.
- 코드를 배포한 뒤 진행 중인 분석이 종료된 것을 확인하고 **서비스 프로세스 전체를 재시작**한다. 파일 갱신/브라우저 새로고침만으로 이미 로딩된 모듈과 세션 객체가 전부 교체되었다고 보장할 수 없다.
- `revision_at_first_runtime`은 해당 프로세스에서 최초 runtime이 만들어질 때 읽은 Git revision이다. 전체 로딩 코드 일치 보증이 아니다. `loaded_delivery_guard`는 실제 로딩된 두 응답 검증 함수의 지문이며 다른 모듈까지 검증하지 않는다. 지문에는 Python/설치 경로 차이도 영향을 줄 수 있다.
- 로그는 현재 파일 약 2 MB와 순환 백업 3개다. 일수 보관이 아니므로 사용량이 많으면 빨리 순환한다. 장애 직후 내부 정책에 맞춰 필요한 로그를 서버 안에서 보존한다. 진단기는 이 4개 파일만 제한된 크기로 읽고 잘린 줄/읽기 실패를 `log_integrity`에 표시한다.
- 예전 실행에는 새 필드가 없을 수 있다. 없는 정보는 미확인으로 취급하며 성공/실패를 만들어내지 않는다.
- 요약에는 SQL/프롬프트/응답 본문/행 데이터/테이블명/접속 주소/토큰을 넣지 않는다. 원본 로그·대화 DB·`.env`를 반출할 필요가 없다. 파일명·ID·버전도 내부 정책상 제한되면 허용된 상태 코드와 익명화한 증상만 전달한다.

계수와 상태는 수치 정답이나 원본 보존 자체를 증명하지 않는다. “다른 조건의 데이터를 분석했다” 같은 의미 오류는 익명화한 기대 조건과 실제 차이를 함께 알려줘야 재현 조건을 만들 수 있다.
