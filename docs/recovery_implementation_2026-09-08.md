# 분석 목표 검증과 복구 구현

## 변경한 동작

- core/analysis_agent/recovery.py: checkpoint에 요청별 차트 목표, 명시된 컬럼, 실제 artifact ID, 실패 상태, 재계획 횟수와 히스토그램 계획을 저장한다. 실패 후 최대 2회 재계획한다. graph 노드 상한은 middleware 단계를 포함하여 64다.
- 실제 PNG, 요청한 차트 종류 및 알려진 컬럼 이름이 일치해야 차트 완료 증거로 인정한다. metadata 성공이나 빈 카드만으로 차트 요청을 완료하지 않는다.
- prepare_histogram은 저장 스키마의 정확한 테이블/컬럼과 필터로 값별 COUNT(*) 계획을 반환한다. 실행기가 query_databricks 호출로 연결하며 기존 HITL/ledger 승인이 필수다. 승인 후 해당 조회 결과를 render_histogram으로 연결한다.
- render_histogram은 완전한 값별 빈도를 가중치로 사용한다. 원본 행을 펼치지 않고 실제 PNG를 만든다. 잘린 결과, 음수/비정수 빈도, 비유한 수치는 거절한다. NULL 수치값은 조회에서 제외한다.
- 원격 실패/거절 뒤 자동 재조회는 차단한다. 복구 예산 소진과 외부 차단을 완료와 구분한다. 검증에서 거절된 임시 답변은 rejected_transcript에 보존하고 대화 본문에서 제외한다.
- 화면은 빈도 히스토그램 카드도 렌더링하며, blocked/exhausted를 성공 상태로 표시하지 않는다. 과거에 이미 저장된 잘못된 답변을 소급 수정하지 않는다.

## 검증 결과

- 새 환경 회귀 28개 및 기존 환경 32개 통과. 승인·거절·재시작·이미지 생성과 계획 후 모델이 멈추는 경우까지 포함한다. 최종 계획 저장/재열기 보완 후 여정 6개 재통과.
- 실제 gemma4:e4b: 원래 후속 질문을 외부 fixture로 재현하여 약 19.4초 만에 승인 대기 도달. DB 호출 0회. live_recovery_validation.json.
- 기존 사용자 대화에서도 브라우저로 동일 질문을 보내 정확한 age 빈도 SQL과 승인/취소 버튼 확인. recovery_browser_evidence.json.
- 첫 실제 시도에서는 문구로 재계획시키는 것만으로 부족했고 graph 노드 상한에 걸렸다. 실패 증거는 live_recovery_initial_failure.json에 보존한다. 이후 실행 계획을 controller로 연결하는 방식으로 보완했다.

## 검증의 범위와 남은 제한

실제 Databricks 데이터의 조회 성공 및 그 데이터로 생성한 이미지는 아직 검증하지 않았다. 현재 사용자 대화는 제품 승인 대기이며 임의로 승인하지 않았다. 이전 OpenSession 403 진단은 별도 연결 문제로 남아 있다. 승인→이미지의 자동 검증은 합성 데이터 executor를 사용하므로 실제 DB 검증을 대체하지 않는다.

현재 자동 계획 연결은 단일 수치 컬럼의 값별 빈도 히스토그램을 지원한다. 복잡한 조인/여러 차트의 작업 완료 조건, 자연어 별칭/필터 해석 정확성, 전체 요청 유형의 의미 검증까지 완성했다는 의미는 아니다. 명시적 차트 키워드와 도구 호출로 목표를 인식하며, 암시적인 모든 시각화 요청을 보장하지 않는다. 단일 실제 모델 성공을 일반적인 지연시간 보장으로 해석하지 않는다.
