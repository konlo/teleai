# 데이터 분석 Agent 설계 재리뷰

검토일: 2026-09-24. 대상: [전체 요구사항](data_agent_requirements_and_evaluation_2026-09-24.md), [EDA 계약](eda_exploration_contract_2026-09-24.md), [릴리스 기준](agent_release_criteria.md).

판정: **기능 방향은 타당하지만 실행 계약·평가 연결을 보강해야 한다.** 아래 8건은 설계의 누락/불명확성이다. 현재 제품의 재현된 버그 8건이라는 뜻은 아니다. 기존 기능별 구현을 전부 다시 감사하거나 실제 모델/DB 평가를 수행하지 않았다. 이번에 문서 계약을 보강했으며 구현 검증은 미완료다.

## 1. 실행 상태와 사용자 방향 변경 — R01

`conversation_id / request_id / plan_revision / step_id / attempt_id`를 실행과 결과에 묶는다. 새 요청이 진행 중 계획을 변경하면 새 revision을 만들고 이전 작업은 취소 요청하거나 이전 revision 전용 결과로 보존한다. 늦은 결과는 현재 계획에 자동 반영하지 않는다. 재사용할 때도 새 계획의 충분성·scope 검증을 거친다.

주요 상태는 `planned → running → verifying → completed`다. 중간에는 `awaiting_approval / awaiting_clarification / recovering`, 종료에는 `partial / failed / cancelled / superseded`를 구분한다. 이는 도메인 상태 명세이며 기존 저장 enum을 즉시 교체한다는 뜻은 아니다. 런타임·UI·checkpoint에 adapter로 매핑한다. 재계획은 revision을 올리고 완료 조건·승인 유효성을 다시 검사한다.

승인 카드가 참조한 계획이 바뀌면 이전 승인으로 변경 SQL을 실행하지 않는다. 같은 질문의 중복 제출은 request idempotency로 처리한다. UI가 끊긴 것과 작업 취소를 구분하며 재접속은 기존 실행 상태를 먼저 조회한다. 전체 프로세스/호스트가 여럿이면 인메모리 lock만으로 중복 실행 방지를 주장하지 않는다.

검증: J17에서 느린 이전 요청 A→조건 변경 B→A 결과 도착, 승인 직전 계획 변경, 두 화면 중복 클릭, 취소 뒤 완료 이벤트를 주입한다. 현재 결과 오염·중복 원격 실행은 0이어야 한다.

## 2. 여러 조회와 snapshot 일관성 — R02

dataset에는 `loaded_at`, 실제 `source_version`(미확인 가능), `schema_fingerprint`, 읽기 범위와 source별 일관성 근거를 분리한다. 로컬 불변 dataset ID의 동일성은 보장할 수 있어도, 별도 원격 조회가 같은 DB 상태를 읽었다는 증거는 아니다.

같은 비율·비교에 필요한 분자/분모는 가능한 한 같은 승인 SQL의 같은 계산에서 얻는다. 여러 쿼리가 필요하면 source adapter가 지원하는 version 고정/일관 읽기 기능을 확인한다. 테이블별 version을 기록해도 여러 테이블의 동일 업무 시점을 자동 보장하지 않는다. adapter가 보장하는 수준만 기록한다.

일관성을 확보하지 못하면 `unknown`으로 남긴다. 일관성이 필수인 결과는 완료로 판정하지 않고, 가능한 단일 조회 계획이나 명시적으로 시점이 다른 비교를 제안한다. 최신 확인을 위해 원격 SQL이 필요하면 승인 정책을 따른다. 로컬 보유 데이터 분석과 현재 원격 상태에 대한 주장을 구분한다.

검증: J18에서 두 집계 사이 원본을 변경하고 같은 적재 날짜·다른 version, schema 동일·데이터 변경, version 미지원 source를 시험한다.

## 3. 분석 의미와 재집계 가능성 — R03

ColumnSpec에는 실제 dtype와 별개로 의미 타입·단위·timezone·범주 순서 및 각 근거를 둔다. 숫자처럼 보이는 ID·날짜 문자열·혼합 단위는 자동 수치형 변환의 근거가 아니다. 명확한 변환은 변환 규칙·실패/제외 건수·원본 lineage를 남기고, 분석 의미가 바뀌면 확인한다. decimal 정밀도·큰 정수·NaN/Infinity·빈 문자열·NULL·DST 경계는 엔진 간 변환 시험에 포함한다.

MetricSpec에는 입력 grain·weight의 의미·필터·NULL 처리·분자/분모·허용 오차와 **재집계에 필요한 통계**를 둔다. 단순 평균은 sum/count가 있어야 합칠 수 있고, 가중 평균은 정의된 weight와 필요한 가중 합이 있어야 한다. 중앙값·분위수는 부분 결과들의 평균으로 합칠 수 없다. distinct count는 집합의 중복 가능성이 있으면 단순 합산하지 않는다. 근사 sketch를 사용한다면 알고리즘/version·병합 조건·오차와 정확성 모드를 명시한다.

공유 집계 cache는 컬럼·필터만 맞는다고 재사용하지 않는다. MetricSpec과 정확성 요구를 만족하는지도 검사한다. 필요한 정보가 소실된 집계만 있으면 더 상세한 보유 데이터로 돌아가고, 그것도 없으면 새 조회 승인을 요청한다.

검증: J19에서 집단 크기가 다른 평균, 집단 간 중복 ID, 부분 중앙값, 숫자형 문자열 ID, 정밀도 경계, 다른 단위/시간대 입력을 독립 oracle로 대조한다.

## 4. 공통 도구 관찰과 복구 책임 — R04

도구가 반환하는 Observation의 필수 계약은 실행 식별자/revision, 도구/version, status, 결과 참조, 실제 scope/coverage/grain, 정확성 모드, 검증 증거, 소요 자원이다. 실패에는 오류 code·실패 단계·retry 가능 조건·원격 제출 상태(`not_submitted/submitted/unknown`)·가능한 복구 동작을 포함한다. 원문 행과 비밀정보 없이 진단 ID로 내부 상세와 연결한다.

도구는 오류와 사실을 반환하고, planner는 그 관찰을 바탕으로 수정 계획을 제안하며, policy/executor는 실행 가능성을 검증한다. 최종 완료 validator는 계획의 필수 산출물·scope·실제 artifact를 검사한다. 모델의 “성공”이나 정상 HTTP 응답은 완료 근거가 아니다. 복구 후보는 지침이며 실행 권한을 추가하지 않는다.

로컬 오류 수정은 남은 예산 내 수행한다. 원격 재실행은 기존 승인 정책을 따른다. 제출 상태 unknown을 retryable 네트워크 오류로 뭉개지 않는다. 실패 fingerprint와 변경된 인자/계획을 기록하여 동일 실패 반복을 제한한다. 계획을 바꾸어도 전체 예산을 초기화하지 않는다.

T02에서 observation/상태/완료 계약의 fixtures를 만들고 T05에서 최소 loop에 연결한다. 이후 모든 capability는 이 인터페이스를 구현한다. T11은 처음 복구 구조를 만드는 단계가 아니라 전체 도구의 통합 실패 주입·보강 단계다.

## 5. 모델 입력과 실행 전체 자원 — R05

큰 데이터는 분석 실행기에 있고 모델에는 필요한 bounded metadata/요약/artifact 참조만 전달한다. 모델 context 예산은 도구 설명, schema, skill 본문, 대화, tool 관찰, 출력 여유를 합쳐 관리한다. 거대한 tool 결과는 잘라서 완전한 결과처럼 전달하지 않고 `truncated`와 전체 참조·선택적 읽기/페이지 정보를 제공한다. 필수 scope·오류·승인·완료 의무는 요약 때문에 잃지 않는다.

노출 필드와 모델 endpoint별 허용 데이터 정책은 preview·로그·평가·export에도 일관되게 적용한다. 운영 데이터 원문 전체를 모델에 보내는 방식으로 context 부족을 해결하지 않는다.

대화별/worker별 한도 위에 호스트 전체 RAM·동시 실행·디스크·원격 실행 수의 admission budget을 둔다. 전역 여유가 없으면 큐에 넣거나 실행 전에 제한을 설명한다. 취소된 worker와 실패한 임시 파일이 계속 예산을 점유하지 않도록 회수한다. UI/메타데이터/모델 프로세스의 자원도 총량에 포함한다.

검증: J20에서 wide schema·긴 tool 오류·큰 프로파일·여러 동시 대화로 context와 전역 예산을 채운다. 의미가 훼손된 잘림, OOM, 대화 간 결과 혼합 없이 제한 또는 완수해야 한다.

## 6. 산출물 발행과 보존 — R06

dataset/aggregate/chart는 `staging → validated → ready` 이후에만 사용자에게 완료 산출물로 노출한다. 실패·중단 시 부분 파일은 ready가 아니다. DB metadata와 파일을 하나의 트랜잭션으로 묶을 수 없다면 임시 저장→검증/digest→최종 위치 확정→manifest commit을 적용하고 재시작 때 미완료 발행을 조정한다.

메모리 cache eviction과 영속 자료 만료/삭제는 다른 동작이다. 진행 중 작업과 아직 유효한 재현 bundle의 참조를 추적하고 삭제 정책을 정한다. 부모 데이터가 만료되면 저장된 차트 표시 가능 여부와 재계산 가능 여부를 분리한다. 오래된 차트를 최신 결과로 취급하거나 숨은 원격 재조회로 복구하지 않는다. 내보내기는 산출물·scope·계산 spec·version을 포함하되 권한 없는 원본 데이터를 자동 포함하지 않는다.

후속 사용자 요구로 보존 정책을 구체화했다. [보호 원본 계약 D08](data_loading_and_preservation_contract_2026-09-24.md)에 따라 활성 EDA root와 참조된 보호 snapshot은 일반 cache/TTL/quota 회수에서 제외한다. 공간이 부족하면 새 적재를 제한하며, 명시 삭제/조직 보존 의무/권한 회수는 별도 정책으로 처리한다. 보존 기간·용량·사용자 삭제 정책은 배포 설정에 명시해야 한다. 실행 중 참조, 취소, 디스크 부족, 저장과 manifest commit 사이 crash, 부모 만료 후 재시작을 J09/J10/J12/J20에 추가한다.

## 7. EDA 완료와 예산 — R07

EDA 계획은 처음에 데이터 특성과 요청에 맞는 **필수 관점**, 선택적 후속 후보, 적용 불가 관점과 사유를 기록한다. 비어 있거나 단변량인 데이터에 부적절한 관계 차트를 요구하지 않는다. 유의미한 패턴이 없더라도 필수 관점의 검증을 끝내면 초기 계획을 완료할 수 있다. 실패한 필수 관점을 나중에 선택 항목으로 바꿔 완료율을 올리지 않는다.

추천 이미지 6개·후속 2단계 같은 제한은 전역 실행 예산 안의 세부 설정이다. 사용자가 명시한 차트는 우선 처리하지만 전체 시간/비용/RAM 한도를 우회하지 않는다. 필수 산출물 미완료 시 partial, 선택적 탐색만 남았다면 초기 계획 완료와 미탐색 후보를 함께 표시한다. 복구·계획 분기·요약·모델 fallback도 전체 예산에 합산한다.

J13/J16에 패턴 없는 데이터와 필수 차트 실패, J15에 명시 차트 다수 요청·예산 소진을 추가한다.

## 8. 모델 실력과 평가 순서 — R08

도구의 기능과 모델의 계획 능력은 별도 검증한다. T02에서 실제 모델의 schema 탐색·복합 요청·후속 변경·오류 복구·EDA 여정으로 작은 기준선을 먼저 측정한다. 모델 ID/서빙 endpoint 버전·추론 설정·context 크기·tool calling 지원·prompt/tool 버전·fallback 여부·지연을 기록한다. 결과를 보고 필요한 모델 설정과 지원 범위를 판단하며 구조만으로 Claude Code 동급을 선언하지 않는다.

각 capability 도입 때 관련 실제 모델 여정을 재실행하고 T12에서는 전수·held-out·반복·성능을 종합 평가한다. 실제 모델 실행이 불가능하면 NOT_RUN/BLOCKED_INFRA로 남기며 대역 통과로 대체하지 않는다. 모델 fallback은 묵시적 외부 endpoint 전송이나 예산 확대가 아니며 허용된 모델 목록·데이터 정책·비용을 지킨다.

E2E가 실제 UI/runtime/executor와 다른 경로를 사용하면 차이를 보고한다. 범용성을 주장하는 held-out 평가는 production fast path를 사용한 결과와 실제 모델이 계획한 결과를 나눠 본다. agent가 실패 후 capability를 unsupported로 바꿔 성공률 분모에서 제거하지 못하도록 평가 manifest의 지원 범위와 채점 분모를 실행 전에 고정한다. 계획한 전체 case 수, 미실행, 인프라 차단, 실패를 함께 보고한다.

## 아직 결정·검증해야 할 사항

- **T01에서 고정**: 초기 출시 chart/분석 capability 목록, 필수 EDA 관점 선택 규칙, 각 요구의 oracle와 실행 가능 test 연결. 현재 문서는 그 산출물을 대체하지 않는다.
- **T02에서 측정**: 사용할 실제 모델의 작은 기준선과 실패 유형. 성능·성공률 목표 초안은 측정 결과로 확정해야 한다.
- **T06~T08에서 확인**: 실제 source의 version/일관 읽기 지원, 배포 RAM/디스크/동시 사용자·보존 정책. 미확인 값은 unknown으로 유지한다.
- **T09 이전 결정**: 격리 분석 코드 실행 backend와 제한을 실제로 강제할 수 있는 환경. 범용 분석을 지원한다고 표시하려면 별도 검증이 필요하다.

이번 리뷰로 핵심 계약을 보강했지만 모든 누락이 없음을 증명한 것은 아니다. 다음 산출물은 추가 기능 나열보다 **요구사항→입출력/상태 계약→fixture/독립 oracle→실행 결과**의 추적표여야 한다.
