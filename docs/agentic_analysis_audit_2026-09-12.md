# 데이터 분석 Agent 구조·신뢰성 진단

진단 완료: 2026-09-12. 대상: 현재 작업 디렉터리의 v1 분석 경로. 구현 수정 없이 코드 읽기, 기존 실행 로그, 임시 합성 데이터·모의 모델/DB 재현으로 평가했다. 여기서 모의 모델 재현은 실제 모델의 오답률 측정이 아니라 실행기가 잘못된 결과를 허용하는지 검사한 것이다.

## 판정

**에이전트 구조는 맞다. 그러나 데이터를 신뢰할 수 있게 분석하는 제품으로 검증되지는 않았다.** 현재는 영속 상태와 승인형 도구 실행을 갖춘 분석 에이전트 초기 구현이다. 데이터 범위, 요청 간 연결, 결과의 완료 조건을 일관되게 강제하는 부분이 부족하다. 일반 데이터 분석 전체를 출시 가능하다고 판단할 근거는 없다.

DataFrame을 보관하는 방식 자체는 적절하다. 문제는 보관 여부만으로 재사용 가능성을 판단하거나, 재사용 검사가 일부 도구 경로에서 생략되는 데 있다. LangChain 교체나 에이전트 수 증가가 우선 해결책은 아니다.

## 실제 실행 구조와 구현된 장점

- `main.py:2`, `pages/Telly.py:7`은 설치된 LangChain major 버전에 따라 경로를 선택한다. 현재 v1 경로는 `ui/analysis_page.py` → `core/analysis_agent/runtime.py`다. 예전 `core/chat_flow.py`만 검토하면 실제 동작을 놓친다.
- `runtime.py:81`: LangChain `create_agent`, LangGraph checkpoint, 모델 → 도구 → 관찰 → 모델의 실제 반복 루프가 있다.
- `assets.py`: DataFrame/메타데이터/PNG를 SQLite에 영속 저장하고, Parquet와 제한된 메모리 캐시를 사용한다. 프로세스 재시작 후에도 결과를 복원할 수 있다.
- `approvals.py:62`: 정확한 조회 envelope, 연결 identity, 원자적 승인 소비와 중복 실행 차단이 있다. SQL을 생성한 것과 실행 승인받은 것을 분리한다.
- `analysis_sql.py:20`: 로컬 DuckDB는 외부 접근 차단, 512MB 메모리, 15초 실행, 20,000행 결과 제한이 있다.
- `analysis_skill_registry.py`: 등록된 Markdown 스킬을 필요할 때 읽고 경로·크기를 제한한다. 실제 PNG 추천도 구현되어 있다.
- 이전 Databricks 403은 토큰 교체 후 세션·테이블 조회 및 승인된 빈도 데이터 조회 성공을 확인했다. 이것이 아래 구조적 정확성 문제까지 해결했다는 뜻은 아니다.

## 주요 발견

### F1 — P1: 계산하지 않은 답도 완료로 인정한다

위치: `core/analysis_agent/recovery.py:36`, `:123`, `:129`; `runtime.py:161`.

완료 조건은 주로 차트 키워드, PNG 유무, 알려진 도구 실패를 본다. 평균·비율·집계 등 일반 수치 요청에 계산 증거를 의무화하지 않는다.

**직접 재현:** 빈 데이터 저장소에서 “보유 데이터의 평균을 계산해줘”에 도구를 호출하지 않는 모의 모델이 “평균은 999입니다.”를 반환했다. 실행 결과는 `answered`, recovery는 `complete`, dataset 목록은 빈 배열이었다.

따라서 자연스러운 답변이나 `complete` 상태는 분석 정확성의 증거가 아니다. 사용자 요청의 지표·범위와 실제 계산 결과를 연결해야 한다.

### F2 — P1: 일부 데이터가 전체 모집단으로 승격될 수 있다

위치: `core/analysis_databricks.py:29`, `utils/analysis_provenance.py:8`, `core/analysis_runtime_tools.py:50`.

원격 결과는 fetch 초과와 LIMIT 중심으로 coverage를 정한다. TABLESAMPLE/OFFSET은 표본·누락으로 인식하지 않는다. 모의 DB 재현에서 두 쿼리 모두 `coverage=complete`, `predicate_known=True`로 저장됐고 전체 범위 재사용 판정이 `reuse`였다.

또한 `use_dataset`의 조건 포함 검사는 `local_analysis_sql`의 필수 선행 단계가 아니다. `value >= 40`으로 제한된 데이터의 전체 모집단 재사용은 `assess_reuse`에서 거절되지만, 같은 데이터에 직접 평균 SQL을 실행하면 `ready`가 나온다. 계산이 틀렸다기보다, 그 결과가 답할 수 있는 모집단을 실행기가 강제하지 못한다.

### F3 — P1: 정상 PNG도 잘못된 통계를 표현할 수 있다

위치: `utils/analysis_charts.py:133`, `core/analysis_agent/recovery.py:84`.

빈도 히스토그램은 weight가 비음수 정수인지만 검사하며 실제 COUNT 집계에서 나온 컬럼인지 검증하지 않는다. 합성 raw 데이터의 `balance=[100,200,300]`를 weight로 넣어도 “빈도 합계 600 · complete” PNG가 생성됐다.

차트 완료 판정도 이미지·종류·컬럼·도구 인자의 dataset ID를 검사하지만 사용자 원래 요청의 출처/필터/기간/모집단과 비교하지 않는다. 그림 생성 성공과 분석 성공은 구분해야 한다.

### F4 — P1/P2: 데이터 재사용 판단이 경로마다 다르다

위치: `core/analysis_runtime_tools.py:50`, `:59`, `:75`; `core/analysis_agent/recovery.py:107`.

모든 로컬 SQL 결과가 `predicate_known=False`로 저장된다. 단순 로컬 필터가 성공한 뒤 그 결과에 평균 SQL을 실행해도 기본 호출은 `needs_data`를 반환한다. `current_result_only=True`라는 경로는 존재하지만, 사용자 의도와 결과 범위를 이어주는 결정은 모델에 맡겨져 있다.

`prepare_histogram`은 기존의 동일 범위 빈도 결과나 PNG를 먼저 탐색하는 실행 계약이 없다. 모델이 이를 선택하면 승인형 재조회 계획으로 진행한다.

**실제 로그:** 2026-09-11 23:11:27에 시작한 동일 `age` 히스토그램 요청은 기존 빈도 78행과 PNG가 보존되어 있었는데도, 23:15:09에 `query_databricks` 승인 대기로 끝났다. 약 222초이며 run ID는 `abab0a4c9d8d4bc2b958b27df5506a60`이다. 이 요청에서 기존 결과 재사용은 검증되지 않았다.

### F5 — P1: 승인 대기 중 변경 요청이 정식 사용자 발화로 기록되지 않는다

위치: `core/analysis_agent/runtime.py:175`, `:190`, `:51`; `memory.py:19`.

승인 대기 중 새 요청을 받으면, 새 내용을 기존 도구의 reject 메시지 안에 넣는다. 새로운 HumanMessage로 갱신하지 않는다. 반면 현재 요청 복원과 완료 판정은 마지막 실제 HumanMessage를 찾는다. 이 두 경로가 서로 다른 목표를 참조할 수 있다.

이 항목은 코드 흐름에서 확인했으며 별도의 실제 모델 변경 요청 여정은 이번 진단에서 실행하지 않았다. 이전 요약 HumanMessage 오인은 수정되어 있지만, 이 변경 요청 경로는 별도로 남아 있다.

### F6 — P2: 복구와 종료 조건이 모든 도구 루프에 적용되지 않는다

위치: `core/analysis_agent/recovery.py:121`, `:135`, `:141`; `runtime.py:43`; `ui/analysis_page.py:40`.

복구 횟수 제한은 모델이 최종 답을 내려고 할 때 증가한다. 도구 호출을 계속 반환하는 반복 실패에는 같은 제한이 직접 적용되지 않는다. LangGraph recursion limit 64는 있으므로 완전 무제한은 아니지만, 업무 목표 단위의 시간·호출·반복 실패 예산과는 다르다.

실제 로그에는 긴 요약/모델 대기와 요청하지 않은 `age × y` 분석 시도가 있었다. 현재 코드에는 원문 요청 복원 보완이 있지만 이를 일반적인 목표 이탈 방지·반복 감지 계약으로 볼 수는 없다.

### F7 — P1: 200/200 PASS는 에이전트 성능 검증이 아니다

위치: `test_set/run_test_set.py:75`, `:90`, `:100`; `tests/analysis_benchmark_100/run_benchmark.py:45`.

평가기에서는 질문을 실제 agent에 전달하지 않고 준비된 `python_code`를 실행한다. 정답과 agent 결과를 비교하지 않으며 예외가 없으면 PASS다.

**직접 재현:** 차트 요청의 `python_code`를 `pass`로 넣었을 때 `PASS`, `has_figure=False`, 빈 stdout을 반환했다.

이 자료는 정답 예제·fixture로 가치가 있다. 하지만 한국어 이해, 후속 질문, 데이터 선택, 조회 승인, 오류 복구, 차트 정확도의 200문항 성공률로 사용할 수 없다. 기존 계약 테스트와 일부 실제 모델 검사는 별도로 존재하지만 전 범위 품질 지표는 아니다.

### F8 — P2: 스킬·차트 추천·로그가 범용 분석을 충분히 뒷받침하지 못한다

- 스킬은 읽을 수 있는 절차 문서다. 스킬별 실행 도구·입출력·완료 검증이 연결된 실행 단위는 아니다.
- 차트 추천은 첫 수치/범주 컬럼과 제한된 그림 종류를 선택하는 규칙 기반 구현이다. 사용자가 지정한 bin, 그룹 비교, 색상, 기존 차트 수정 등을 위한 일반적인 명세/편집 도구는 없다.
- `diagnostics.py:24`의 run/error 이벤트는 유용하다. 다만 모델·요약 호출별 시간, 구조화된 목표/범위, 재사용 판정 사유, 계산 결과-답변 연결 증거가 충분히 기록되지 않는다. 원문과 비밀값을 로그에 그대로 추가하는 방식으로 해결해서는 안 된다.

## 개선 순서

1. **분석 완료 계약:** 지표/집단/기간/필터/분모/출력 형태를 구조화하고 실제 계산·자산과 대조한다. 숫자와 PNG 유무만으로 완료 처리하지 않는다.
2. **데이터 사용 단일 경로:** 모든 로컬·원격·차트 도구 전에 같은 범위/집계/표본/출처 검사를 적용한다. 요청 범위가 없으면 모델의 선언만으로 전체 분석을 허용하지 않는다.
3. **후속 요청과 파생 결과 연결:** 사용자 요청, 승인 결정, 요약을 구분한다. 단순 필터/투영의 lineage를 보존하고 집계 재사용 가능 조건을 명시한다.
4. **유한한 복구:** 동일 실패 반복 감지, 전체 호출·시간 예산, 도구 오류 유형별 대안, 완료 후 불필요한 후속 도구 차단을 둔다.
5. **실제 agent 평가:** 기존 정답 세트를 oracle로 활용하되 입력은 자연어로 실제 runtime.submit에 전달한다. 결과·모집단·조회 횟수·승인·실제 이미지·지연시간을 자동 검증한다. 단일 질문과 다중 턴을 분리 보고한다.

기존 LangGraph/승인 ledger/영속 자산/안전한 로컬 SQL/스킬 registry는 유지할 수 있다. 위 계약을 그 사이에 일관되게 연결하는 보완이 우선이다.

## 검증 범위와 한계

- 이번 진단에서는 production 코드를 변경하거나 신규 원격 쿼리를 실행하지 않았다. 기존 진행 중이던 UI 실행 로그는 읽기만 했다.
- 주 에이전트가 무계산 수치 완료와 빈 차트 benchmark PASS를 임시 환경에서 재현했다.
- 데이터 계약 독립 진단이 합성 데이터·모의 DB로 F2/F3/F4 경로를 재현했고 관련 기존 계약 테스트 26개 통과를 보고했다. 이 개수는 다른 검사와 중복 가능하므로 합산하지 않는다.
- 앞선 수정 과정의 16개 계약 검사 통과와 실제 Databricks 로딩 성공은 개별 기능 증거다. 전체 agent 출시 준비 완료를 뜻하지 않는다.
- 전체 자연어 정확도, 다중 턴 성공률, 대용량 최대 메모리, 응답 시간 목표 충족 여부는 이번 진단으로 확정하지 않는다.
